# Platform providers and runtime readiness

Use with common Platform and Backend safety. Read [provider model](../../../../docs/architecture/provider-model.md), [security model](../../../../docs/architecture/security-model.md) and [orchestrator architecture](../../../../.github/instructions/orchestrator-architecture.instructions.md) for the affected capability.

- Locate the existing application port, provider adapter, configuration schema and actual composition root before extending a capability. Keep vendor SDK/CLI/protocol types inside adapters. Constructor injection and explicit composition apply the shared substitution principles without Nest DI or Archipel runtime dependencies.
- Inspect installed Synapse package capabilities and the current Symphony adapter before adding CLI/auth/process/routing machinery. Synapse owns its library contract; Symphony owns product workflows, workspace/account policy, catalog/routing/failover policy and durable application state. Fix or coordinate an owned library defect through its source/release path instead of copying the library into Symphony.
- CLI execution adapters remain replaceable details. Resolve supported account/model capabilities through the actual configured runtime and product policy; installed dependencies are not evidence of authenticated availability. OmniRoute remains research-only and never becomes a runtime, provider, catalog or example.
- Reuse `libs/configuration` and the application bootstrap. Validate versioned settings and provider registration early; capture environment only at its existing owner. Common `ConfigService`/`createConfigKey` examples do not authorize a second loader or secret store.
- Keep workspace, account, execution and resource scope explicit per operation. Do not retain a mutable current user/account/workspace in a singleton. Preserve isolated credential/runtime homes and opaque references; redact provider secrets and raw payloads from logs, errors, telemetry and persisted evidence.
- Keep network/process startup out of constructors. Own initialization, subscriptions, native processes, streams, timers, cancellation and bounded shutdown through the existing lifecycle. Preserve safe disposal ordering and pending-call failure behavior when the Utility Process exits.
- Bound payloads, deadlines, retries, concurrency, buffers, registries, caches, queue/retention depth and output. Retry only transient safely repeatable work with the existing idempotency/continuation policy. Read-only routing failover does not authorize replaying writes or a started implementation.
- Validate untrusted external destinations at the actual connection boundary, including redirects and response bounds. Public-HTTPS examples apply to external HTTP features; they do not ban native CLI stdio, owned login callbacks or the explicit private-network mobile companion.
- Reuse structured logging and correlation through `libs/logging`; keep diagnostics actionable at the related problem's owner. Generic health state, storage locality, process boundaries or security claims do not become workspace decoration.
- Review provider/configuration changes across public entrypoints, manifests, consumers, lifecycle, error projection and docs. Check meaningful startup failure, account/workspace isolation, cancellation, resource bounds and cleanup. Leave package publication and releases within the user's actual authority.
