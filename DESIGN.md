## Overview

Symphony is an Electron desktop application. Its renderer is a zoneless Angular app that
composes **Mosaik** — Lit web components consumed through `@pixel-brewery/mosaik-elements-angular`.
Mosaik is the design system. Symphony does not maintain a parallel semantic token layer: it
selects the Mosaik **Soho** theme — the visual language of shadcn/ui (style Vega, base colour
Neutral) — supplies an override object that Mosaik deep-merges into it at startup (currently
empty, so Soho's values apply unchanged), and every resulting value is published as a
theme-agnostic `--mosaik-*` CSS custom property.

The wiring lives in two files:

- `libs/frontend/ui/src/lib/theme/ApplicationThemeOverrides.ts` — the override object.
- `apps/renderer/src/configuration/ShellConfig.ts` — `provideTheme({ theme: SohoTheme.SOHO_THEME, mode, overrides })`,
  the complete Reicon system set, plus product aliases through `provideIcons()`. The mobile app
  (`apps/mobile/src/app/app.config.ts`) applies the same
  overrides, so this document governs both surfaces.

Symphony's look is Soho's: **a white canvas, near-black text and a near-black primary action, quiet
neutral fills, 1px light-grey borders and small soft shadows** — flat surfaces, Inter at `text-sm`
for every control, nothing that glows or moves on hover. The window chrome follows the same rule:
the title bar is the shadcn site header (`bg-background` with a 1px bottom rule), exactly as light
as the content below it. Restraint is the point; do not add gradients, tinted chrome, coloured
shadows or decorative backplates.

Use this precedence whenever sources appear to disagree:

1. Mosaik component APIs and Mosaik theme/component token sources.
2. The effective theme: the Mosaik Soho baseline plus Symphony's overrides.
3. Shared Symphony component overrides that consume Mosaik tokens (`libs/frontend/ui`, `apps/renderer/src/styles/overrides`).
4. This DESIGN.md projection and its prose.

This file is an agent-readable projection into Google's DESIGN.md format; its `components`
block carries the core atoms with the overrides Soho applies, and `COMPONENTS.md` beside it holds
the complete component-token model with the values Symphony renders.

## Colors

Use Mosaik's active aliases, never a copied hex value:

```css
color: var(--mosaik-scheme-foreground);
background-color: var(--mosaik-scheme-surface);
border-color: var(--mosaik-scheme-highlight);
```

- `--mosaik-scheme-*` describes the active surface and content relationship: `surface`, `background`,
  `foreground`, `highlight`, `middlelight`, `lowlight`, `transparent`, `semi-transparent`, `disabled`,
  `contrast`, and `selection`.
- `--mosaik-color-{family}-{shade}` exposes the active palette ramp for `primary`, `secondary`,
  `tertiary`, `info`, `warning`, `danger`, `success`, `highlight`, and `neutral`.
- Component appearances and variants decide which palette shade belongs to rest, hover, active, focus,
  selected, and disabled states. Do not invent aliases such as `primary-hover`, `on-primary`, or
  `surface-card` outside Mosaik.
- Use the Mosaik semantic variants for status. `danger`, `warning`, `success`, and `info` are not
  interchangeable brand accents.
- In Soho `primary` is the near-black (light) / near-white (dark) action colour, and `secondary`,
  `tertiary` and `highlight` are teal, orange and violet derivations. None of them is a neutral
  chrome colour: a coloured variant on `solid` renders Vega's soft tint (10 % of the variant with the
  variant text), so never reach for `tertiary` or `secondary` to get a quiet button.
- `--mosaik-scheme-semi-transparent` is the black-at-50 % scrim behind modal overlays, not a
  translucent surface; never paint chrome with it.

Symphony ships **both modes**. `resolveInitialThemeMode()` picks the mode from the user's stored
preference, falling back to the OS setting, and the in-app theme toggle switches it at runtime. The
DESIGN.md schema has no light/dark dimension, so the generated color values are the effective

## Typography

Use the exact Mosaik typography roles: `headline1` through `headline6`, `subtitle1`, `subtitle2`,
`body1`, `body2`, `supporting`, `caption`, `overline`, and `button`. Symphony uses Soho's values
unchanged and never renames them to `display-*`, `title-*`, or `label-*`.

One sans stack carries every UI role; the exact families are in the `typography` frontmatter above.
Monospace is **not** the interface font — it is reserved for technical values (ids, hashes, paths,
branch names, sizes) through the shared `.technical-value` class in
`apps/renderer/src/styles/overrides/technical-value.scss`. Reach for that class when the content is
machine-shaped, and never set a font family inline to get the same effect. Inter is packaged locally
(`libs/frontend/ui/src/lib/theme/fonts.scss`) because Soho is set in Inter; every role still keeps a
real fallback stack. Do not introduce a display face.

Prefer the Mosaik shorthand when styling shared CSS, and the individual properties only when a
component custom-property contract requires them:

```css
font: var(--mosaik-typography-body1);
font-size: var(--mosaik-typography-body1-font-size);
line-height: var(--mosaik-typography-body1-line-height);
```

Mosaik components already select the correct typography token. Feature code should normally choose the
right component or variant rather than restyling its font. When custom composition is necessary,
preserve each role's size, weight, line height, and letter spacing as one unit. Do not use Tailwind
typography utilities or arbitrary font values.

## Layout

Mosaik owns the base layout tokens; Symphony uses Soho's values for all three:

- `--mosaik-layout-space` — the spacing unit.
- `--mosaik-layout-radius` — the shared radius.
- `--mosaik-layout-thickness` — the shared border and focus-ring thickness.

Their current values are in the `spacing` and `rounded` frontmatter above; read them there rather than
repeating them in prose, so this section cannot go stale.

Tailwind v4 is in use on both Angular surfaces, layered on `@pixel-brewery/mosaik-themes/tailwind/v4/soho`.
Its `--spacing` is deliberately kept equal to `--mosaik-layout-space`, so classes such as `gap-2` and
`p-3` remain multiples of the Mosaik rhythm; `mosaik-design-md` fails if that stops being true.
Those classes are layout syntax, not a second token system. Tailwind's `--radius` should track
`--mosaik-layout-radius` too, but only warns, because feature code is not supposed to reach for
`rounded-*` at all.

Tailwind is allowed only for structural layout: display, grid/flex composition, positioning, sizing,
overflow, responsive behavior, and margin/padding/gap. Do not use it for colors, typography, radii,
shadows, borders, or component states; use Mosaik components and `--mosaik-*` tokens instead. The
preset's generated `--color-*` values are not Symphony's runtime theme contract.

Custom utilities that do carry appearance (`surface-input`, `ai-border-spin`, and the rest of
`apps/renderer/src/tailwind.css`) are a deliberate, reviewed set built on `--mosaik-*` values. Extend
that file rather than scattering equivalent literals through feature code. Soho surfaces are flat:
do not add gradient backplates behind content.

Preserve the existing shell, responsive composition, and scroll ownership when extending a view. Use
the `scrollable-container` / `scrollable-content` pair for scroll containment rather than inventing a
new flex chain. Density must not erase labels, focus affordances, or the sizing behavior of the
selected Mosaik control.

## Elevation & Depth

Use Mosaik elevation tokens (`--mosaik-elevation-*`) and the elevation already selected by the
component. Prefer scheme contrast, borders, and spacing before adding depth. In Soho `light` is
`shadow-xs` (controls, cards), `semilight` `shadow-sm`, `regular` `shadow-md` (popovers, menus) and
`semibold` `shadow-lg` (dialogs, sheets); chrome bands such as the title bar carry no shadow and no
backdrop blur. Overlays, menus, drawers,
sheets, cards, and buttons inherit their established elevation from Mosaik or a shared Symphony
override.

Do not use Tailwind shadow utilities or feature-local box-shadow literals. If a shared component
genuinely needs a different elevation, change its component-token mapping or shared override with a
Mosaik elevation token.

## Components

Choose components in this order: an existing Mosaik component, a shared Symphony composition from
`libs/frontend/ui`, then feature-owned composition. New feature code must not reproduce controls that
already exist at either shared layer.

Mosaik component tokens have their own richer contract and precedence: base component defaults, opt-in
token mixins, then theme-specific component tokens. Symphony maps a component's public custom
properties in shared override styles, but those values should resolve back to `--mosaik-*` tokens.
The `components` frontmatter projects the core atoms of that model, each with the appearance,
variant and state overrides Soho applies for `primary`; the complete hierarchy, every component
token with the value Symphony renders, is `COMPONENTS.md` beside this file.

The design language lives in props, not in a utility-class vocabulary:

- `variant` — `default | primary | secondary | tertiary | danger | warning | success | info | neutral | highlight`.
  This is the semantic color axis; use it instead of hand-picking colors.
- `appearance` — `default | outline | plain | soft | solid`. How much the surface asserts itself.
- `size` — `tiny | small | medium | large | giant`.
- `elevation` — `none | light | semilight | regular | semibold | bold | extrabold`.
- `inset`, `fit`, `orientation`, `disabled`, `isBusy`, `isSelected` — spacing, sizing, direction, state.

Not every component accepts all of them; the component's own typings list what it takes.

Per area:

- **Actions:** Use Mosaik button appearances and variants and let their component tokens own rest,
  hover, active, focus, and disabled styling. Preserve the distinction between an action button and
  `mosaik-press-button` toggle/press semantics. The Soho mapping follows shadcn: `solid` is the one
  primary action of a view, `outline` (or the default appearance) the secondary toolbar action such as
  Filter or Refresh, `soft` the quiet secondary button, and `plain` the ghost icon button — the
  "More actions" trigger on a row or card. None of them needs a colour variant.
- **Forms:** Use Mosaik form-field and input controls so label, help, validation, disabled, focus, and
  keyboard behavior stay coherent. Preserve the actual control type.
- **Cards and pages:** Use the Mosaik/shared page and card shells and their slots; do not recreate their
  surface, padding, radius, or elevation with utilities. The default appearance is the Vega card
  (surface fill, 1px hairline, `shadow-xs`); `soft` is a borderless muted fill for nested or
  secondary content, not the resting card.
- **Collections and navigation:** Reuse the established Mosaik table, list, paginator, tabs, breadcrumb,
  menu, selection, empty-state, and loading patterns.
- **Overlays:** Dialogs, drawers, sheets, popovers, and menus inherit Mosaik focus, dismissal, layering,
  and responsive behavior. Close actions stay idempotent.
- **Feedback:** Use Mosaik badge, notification, progress, skeleton, and status variants. Color alone must
  not carry meaning.
- **Loading:** A loading state is the loaded layout with its unknown values missing. Render the real
  containers (page header, cards, cell groups, list rows, columns, expanders, timelines), keep static
  headings and labels readable, and put `mosaik-skeleton` lines only where data will appear, sized to the
  line box of the text that replaces them. Controls whose look does not depend on data render disabled
  rather than as blocks. Never show a default value (an empty board, an "off" switch) that the data
  might contradict, and never hide content with the `hidden` attribute on an element that carries a
  Tailwind display utility: without Preflight the utility wins.
- **Motion:** Keep motion purposeful and respect reduced-motion preferences. Continuous motion is
  reserved for a real active process.

## Renderer Stylesheet Overrides

<!-- design-md:overrides -->

`apps/renderer/src/styles/mosaik.scss` loads the theme stylesheet and these 4 override files from `apps/renderer/src/styles/overrides/`:

`app`, `app-header`, `technical-value`, `window-chrome`
<!-- /design-md:overrides -->

Put a reusable visual override here, at the shared component boundary, rather than in feature code.
These files style Mosaik's shadow parts and component custom properties; they are the sanctioned place
to bend a Mosaik component to Symphony's shell geometry or to restore structure a third-party library
needs. They set no colour of their own beyond Mosaik tokens.

## Local Design System Files

The design system is also available as browsable files, so agents and people can read the real
component contracts instead of guessing. It is built from Symphony's own theme by the `.design-sync/`
pipeline (see `.design-sync/NOTES.md`) into `.ds-sync/artifact/project/` and published as the
"Symphony Design System" artifact that Design canvases copy:

- `README.md` — the conventions, the foundations and an idiomatic screen.
- `components/<Name>/` — `README.md` (what it is, its slots and parts, a verified example),
  `<Name>.d.ts` (exact props and allowed values) and `preview.html` (live variant grid).
- `components/bundle.js`, `components/bundle.css` — the React wrappers on `window.Mosaik` and this
  renderer stylesheet; `tokens.json` / `tokens.css` — the measured Soho tokens, light and dark.
- `.design-sync/previews/` — the hand-authored preview sources.
- `.design-sync/docs/` — per-component documentation generated from Mosaik's source.

`.ds-sync/` and the generated parts of `.design-sync/` are gitignored because they are large and fully
regenerable; rebuild them with the pipeline in `.design-sync/NOTES.md`. This DESIGN.md is the
committed, always-current projection of the same system — regenerate it with `yarn design:md`.

## Do's and Don'ts

### Do

- Read this file, then inspect the actual Mosaik component API (`ds-bundle/components/...`) and a working
  Symphony sibling before changing UI.
- Use Mosaik components first and consume the active `--mosaik-*` aliases in shared styles.
- Use Tailwind only for structural layout and its Mosaik-aligned spacing multiples.
- Keep light and dark behavior paired by relying on the active aliases rather than mode-specific literals.
- Preserve control semantics, keyboard access, focus visibility, validation, loading, empty, error,
  disabled, and selected states.
- Put reusable visual overrides at the shared component boundary and keep feature-owned behavior in the
  feature.
- Verify meaningful visual changes in the running app at desktop and narrow widths, in both modes.
- Run `yarn design:md` after touching the theme overrides, the icon registration, or the override
  stylesheet list.

### Don't

- Do not treat `ApplicationThemeOverrides.ts` as a separate design system; it is an override layer on
  Mosaik Soho.
- Do not invent Symphony aliases, component tokens, typography role names, or light/dark token namespaces.
- Do not copy values from the generated YAML into CSS. Use the corresponding `--mosaik-*` custom property.
- Do not use Tailwind color, font, radius, border, or shadow utilities for visual styling.
- Do not hard-code feature-local colors, spacing, radii, borders, typography, or shadows when Mosaik owns
  the decision.
- Do not replace Mosaik controls with native or one-off lookalikes, and do not silently change a
  control's interaction model.
- Do not use an icon name that is not registered, and do not assume a missing icon will show a fallback.
- Do not update only one color mode, bypass component states, or rely on color alone to express status.
