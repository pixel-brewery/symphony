# Symphony Technical Docs

Keep `docs/architecture` as the feature-oriented technical handbook for Symphony. Document the system deeply enough that an implementation-capable reader can reconstruct the owned behavior, contracts, boundaries, failure handling, and verification in another project. Treat technical documentation as part of implementation completion.

## Establish the contract

1. Read `AGENTS.md`, `docs/README.md`, `docs/architecture/README.md`, the affected functional pages under `docs/project`, and every existing technical page for the feature before editing.
2. Treat source code, executable configuration, schemas, generated contracts, migrations, focused tests, and verified runtime behavior as evidence for implemented behavior. Treat existing prose only as a lead until reverified.
3. Distinguish an implemented current state from an accepted target architecture and from a migration contract. Never present a proposal, partial path, or desired guarantee as implemented.
4. Preserve unrelated worktree changes. For ordinary implementation work, use the task-scoped diff as the starting scope and broaden only along affected contracts and consequences.

## Select the mode

- **Build:** Create the technical feature documentation when no trustworthy page exists. Read [technical-feature-guide.md](references/technical-feature-guide.md) and [coverage-checklist.md](references/coverage-checklist.md), then reconstruct the capability end to end from evidence.
- **Synchronize:** After implementation, update every affected technical contract, including removals, changed guarantees, and new failure or migration behavior.
- **Audit:** Test whether a requested technical feature can be implemented from its documentation alone. Verify every material claim and correct or report every confirmed gap.
- **Migrate:** Move a legacy technical document into the feature-oriented architecture tree, reverify its claims, repair inbound links, and remove the superseded path. Git is the archive.

## Place documentation by feature

1. Use `docs/architecture/<feature>/README.md` as the stable technical entry point. Reuse the corresponding `docs/project` feature slug when the product feature owns the capability.
2. Give a cross-feature platform capability its own narrowly named feature folder when no single product feature owns it. Name the folder after the capability, never after a repository layer or generic bucket.
3. Add sibling Markdown pages only for independently implementable contracts, substantial variants, or migrations that would make the entry page difficult to scan.
4. Do not organize technical documentation by `backend`, `frontend`, `database`, `apps`, `libs`, `shared`, package, framework, or deployment target. Those are participating boundaries inside a feature document.
5. Keep `docs/architecture/README.md` synchronized as the complete index. Create no new standalone technical Markdown file at the root of `docs` or directly below `docs/architecture`.
6. Keep change requests, proofs of concept, transient analyses, release notes, and unaccepted plans outside the canonical technical handbook.

## Investigate end to end

1. Define the technical capability by its outcome, guarantees, inputs, outputs, state, owners, and consumers.
2. Trace all participating runtimes and layers: composition roots, public exports, frontend state and UI boundaries, generated transport contracts, backend services and policies, persistence, jobs, files, providers, events, webhooks, email, and deployment configuration as applicable.
3. Identify the canonical owner and dependency direction. Search for legacy paths, bypasses, and equivalent implementations before describing one path as authoritative.
4. Build a working evidence map containing:
   - responsibility and canonical owner;
   - public contract and callers;
   - validation, permission, tenant, availability, and limit boundaries;
   - state, lifecycle, transaction, concurrency, and idempotency behavior;
   - side effects, integrations, observability, and recovery;
   - configuration, runtime, provider, compatibility, migration, and rollback obligations;
   - focused tests and executable validation.
5. Apply [coverage-checklist.md](references/coverage-checklist.md). Mark a topic not applicable in working notes rather than filling the published page with generic prose.

## Meet the portability standard

A technical page must remain implementable when copied without this repository:

- Define every required responsibility and guarantee semantically before naming its current Symphony file, package, class, route, key, table, or provider.
- Include the complete behavior needed for implementation. A repository link may prove or locate a claim, but must never be the only explanation of that claim.
- State framework, library, provider, and platform assumptions. When a dependency supplies a guarantee, describe both the consumed contract and the responsibility a replacement must satisfy.
- Specify public and persisted contracts precisely enough to recreate them, including validation, ownership, versions, errors, ordering, and compatibility where material. Use compact examples or schemas when prose would be ambiguous.
- Separate stable domain or capability rules from source-project placement. Put exact paths and symbols in an implementation map that can be replaced in another repository.
- Define observable acceptance criteria and meaningful negative cases. Do not rely on snapshots of incidental source structure or on tests that pin presentation details.
- Record unresolved decisions explicitly. If a missing decision changes the safe implementation, do not conceal it behind an assumed default.

## Write the technical handbook

- Write new narrative in German unless an exact external contract or established feature page requires another language. Preserve exact technical identifiers when they are part of a real contract.
- Start every feature or capability page with one documented status from the technical feature guide.
- Lead with the objective, scope, guarantees, and ownership. Then describe architecture, contracts, execution flows, state, policies, failures, operations, migration, and verification where relevant.
- Use diagrams, state tables, sequence tables, schemas, or examples only when they remove implementation ambiguity. Explain every important branch in text or table form.
- Describe both success and failure behavior, including denied access and the absence of side effects where that is a guarantee.
- Keep product value, visible workflows, and business rules canonical in `docs/project`; link to them instead of publishing a second functional handbook. Keep source mechanics and technical contracts canonical in `docs/architecture`.
- Never include secrets, credentials, private environment values, real customer data, or an unsafe operational command.

## Synchronize after implementation

1. Review the task-scoped diff and list changed technical responsibilities, contracts, state, configuration, security boundaries, providers, consequences, and acceptance evidence.
2. Search `docs/architecture` by feature language, technical identifiers, routes, models, events, configuration keys, permissions, errors, providers, and owning paths.
3. Update every affected page, not only the first search result. Remove obsolete guarantees and repair renamed or moved links.
4. Update `docs/architecture/README.md` when a feature entry is added, renamed, migrated, or removed.
5. For a change with no technical contract impact, make no artificial edit; record the completed check and the concrete reason.

## Validate before completion

1. Re-read every changed technical claim against implementation, accepted decisions, and focused tests or runtime evidence.
2. Apply the portability test from [coverage-checklist.md]: a fresh Codex instance with only the page and named public dependencies must be able to plan a faithful implementation without guessing material behavior.
3. Search the affected feature for superseded identifiers, contradictory ownership, stale guarantees, and undocumented bypasses.
4. Run `node .agents/skills/symphony-technical-docs/scripts/validate-technical-docs.mjs docs`.
5. Run `node .agents/skills/symphony-docs/scripts/validate-docs.mjs docs` and `git diff --check -- <changed-documentation-and-skill-files>`.
6. Report:
   - technical features and pages created, migrated, synchronized, or audited;
   - the principal implementation evidence and canonical owners followed;
   - portability, structure, and link validation performed;
   - unresolved decisions or implementation gaps; or
   - the concrete reason no technical documentation file changed.
