# Execution lifecycle

Analysis has two explicit branches. Manual completion transitions a backlog item to the provider-neutral `ready` state and immediately persists the user's Markdown as a successful `manual` execution without resolving a skill, preparing a workspace, or invoking an agent. The opt-in AI branch additionally resolves the workspace's assigned analysis skill and agent profile, acquires distributed work-item ownership when the source exposes that capability, prepares a detached read-only workspace, persists a running `ai` execution with an immutable provider-binding snapshot and any ownership proof, composes context, streams agent progress, validates the summary, and persists success. GitHub Projects require this capability; providers without a shared coordination primitive retain the existing installation-local guard. Re-analysis follows the selected branch and creates a new immutable execution without moving an already claimed item out of its current state. AI exceptions preserve the workspace, persist the classified execution error, and leave the durable work-item state unchanged. Analyzer and Solver never assign users. They may project only the provider-neutral `Assistant phase` action through the coordination port; provider-specific field IDs and mutations stay in the adapter. Both branches publish the completed analysis on the tracked item; see Result publication below.

Implementation starts only from a successful analysis. Manual completion transitions the work item to provider-neutral `executing` and records the user's Markdown as an immediate successful solution or revision without a skill, worktree, or agent. The opt-in AI branch additionally requires an assigned solution-role skill and creates an isolated worktree on a real `codex/work-<item>-<slug>` branch from the repository binding's configured default branch. A collision receives an execution-derived suffix so every new implementation attempt has a distinct local branch. The provider-neutral branch reference and exact workspace, work-item, repository, CI, and AI bindings are persisted on the execution, streamed as the workspace event, and shown in Task and Run details while the selected agent has `workspace-write` only inside that worktree. Success, failure, and user cancellation leave the item in `executing`; execution state distinguishes active, successful, failed, and cancelled attempts. A successful prior solution changes the next completion into a revision. AI rework requires explicit feedback persisted on the execution and passed to the Solver; manual rework records the completed changes. Agent runs never commit, push, merge, or mutate tracker metadata beyond the explicit state transition owned by orchestration.

Before Analyzer or Solver can claim or transition a work item, it must resolve one enabled repository binding in the work item's Workspace Definition and that repository must be locally prepared. Adding and enabling the binding is the operator's authorization for manual, remote, and autonomous AI work; no second repository-trust prompt or grant is required. Calls stop before shared claims or tracker transitions when repository selection is ambiguous or local preparation is missing.

Every AI analysis and implementation run starts from the complete work item, never from a board summary. The runtime prompt carries the provider discussion thread beside the body, oldest first and introduced as untrusted task data like the body, because comments hold decisions the body never received; an oversized comment is cut with a visible marker so one long thread cannot displace the skill instructions.

SQLite writes occur before their corresponding event is published to the renderer, so a refresh cannot observe an event without its durable record. While an AI run is active, visible agent messages, reasoning summaries, commands, file changes, and tool/status updates use the same ordered event path and appear immediately in its Run drawer. A provider continuation is durably stored as an opaque value together with the immutable binding and work-item snapshots, managed workspace, branch reference, attempt, and heartbeat. Terminal result, failure, cancellation, and recovery remain lifecycle events rather than a second activity model. A per-work-item guard rejects a second active Analyzer or Solver execution. A second application-wide guard atomically reserves the configurable parallel-execution capacity before any tracker or workspace mutation, so simultaneous UI, mobile, remote, and [autonomous](autonomous-execution.md) starts obey the same bound. AI executions have no elapsed-time deadline. The user may explicitly pause one running execution from the macOS menu-bar panel; Symphony terminates its live child safely, persists an operator-owned `waiting` pause with the provider continuation, and releases its capacity slot without releasing the workspace or shared work-item claim. Resume clears that pause and continues the same execution. If capacity is full, the durable pause records the resume request and starts automatically in request order when a slot becomes available, including after restart. This operator pause remains distinct from lifecycle pause and explicit cancellation. A start that finds every slot taken is not refused: the step is recorded as a durable queue entry carrying the work item, role, prompt, and granted local-execution approval, without a workspace, a shared claim, or an agent session. Queue entries survive restart, consume no capacity, and are ordered oldest-first. Symphony drains them automatically whenever a slot is released, at startup, when the parallel-execution limit is raised, and at the start of an [autonomous](autonomous-execution.md) cycle - independently of whether autonomous work is enabled. A requested operator resume is filled before the queue, and the queue before any new autonomous selection. Every guard is applied again when a queued step actually starts; an entry that cannot start yet keeps its place with the recorded reason while the drain continues with the next one. The operator may withdraw a queue entry at any time from the workspace rail, the Task drawer, the board card menu, or the mobile companion; nothing was reserved for it, so removal has no further effect. The user may explicitly cancel a running or waiting execution; the cancellation signal crosses the typed process boundary, terminates the owning agent process, persists `cancelled`, applies the configured failed-workspace retention policy, and publishes `execution.cancelled`.

[Agentic pull-request delivery](agentic-delivery.md) uses this same lifecycle with specialized `ci-diagnosis` and `ci-repair` skill roles. Both retain the original managed implementation worktree across terminal diagnosis and restart recovery; they cannot be mistaken for the ticket's normal successful analysis because the immutable flow role is part of the execution record.

## Result publication

Every completed step is written back onto the tracked item, so the ticket carries the result and not only the local run history. Four notes exist: the analysis report, the implementation or revision report, the pull-request handoff, and the human acceptance decision. Each carries a headline, the report text, and labelled details - the delivered pull request and the implementation branch, the recorded decision. A managed branch is only addressable once it is pushed with its pull request, so an implementation that has not been delivered yet names its branch without a link.

The application composes a provider-neutral note and the work tracker turns it into its own record - an issue comment on GitHub Projects. Publication is best effort and deliberately never authoritative: a provider without note support, an item with no issue behind it, and a rejected write are recorded on the run stream and never turn a succeeded step into a failed one. The durable artifact remains the execution record in Symphony; the note is a readable copy. A report longer than the provider's comment limit is cut with a visible marker rather than rejected as a whole.

## Distributed work-item ownership

Local SQLite guards protect one installation; they are not used as a cross-machine lock. The GitHub adapter acquires a deterministic repository ref under `refs/heads/symphony/claims/<work-item-hash>` with GitHub's atomic create-ref operation. Exactly one contender can create that ref, regardless of GitHub assignees or the authenticated contributor account. After winning, it advances the ref to an empty metadata commit containing the authenticated GitHub login, action, execution ID, and Project item ID. The opaque ref-and-commit token is stored as a provider-neutral `WorkItemClaim` on the execution. Every phase advance and release rereads the ref and compares its commit ID before mutating `Assistant phase` or deleting the ref; an installation never releases a token it did not acquire. Refreshing the Project resolves active `Analyze` and `Solve` actions back to their remote claim metadata. The renderer compares that token with locally persisted execution claims and shows a foreign-instance lock on the Board card and Task detail without treating assignees as owners.

Ownership spans the successful Analyzer-to-Solver handoff because the durable analysis artifact is local; the note published on the ticket is a readable copy, not the handoff source. Analyzer success changes the action from `Analyze` to `Solve` but retains the same claim. Pauses, transport interruptions, and failed attempts also retain it so the owning installation can recover or retry against its persisted execution and workspace. Solver success and explicit user cancellation set the action to `None` and delete the claim ref. Revisions acquire a new claim. There is deliberately no time-based expiry or automatic stealing: a slow or partitioned owner must never overlap a replacement. If a machine is permanently lost, an operator must inspect the metadata commit and explicitly delete only that ticket's claim ref before another contributor can continue it.

The application-wide quit path uses the same runtime ownership rather than killing the Utility Process first. Active execution and Work Item Creator registries are inspected before quit. Keeping work in the background preserves the live process graph and stream. For Analyzer and Solver work, quit-and-resume aborts the live child as an infrastructure pause, durably retains `waiting`, and waits for that handoff before Main exits; startup then resumes the saved session. Cancel-and-quit is distinct: it aborts all registered operations concurrently and persists terminal user cancellation before exit. Cancellation and pause have a bounded child-termination grace period only after the user explicitly requests either lifecycle action; this is not an execution runtime deadline.

Loss of network connectivity, Wi-Fi changes, provider transport failures, and sleep/wake interruptions are non-terminal. Symphony persists Analyzer and Solver executions as `waiting`, retries with bounded exponential spacing but no attempt limit, and asks the bound runtime to resume the opaque provider session. Codex uses `codex exec resume`, Claude uses its session-resume interface, and OpenCode uses `opencode run --session`. If the provider no longer has that session, Symphony clears only the opaque continuation and starts a replacement against the same immutable bindings, durable workspace, and task snapshot. The waiting state remains visible on the Board, Home, Task drawer, and Run rail, retains the progress ring, and stays cancellable. The active Work Item Creator request uses the same unlimited provider retry while its drawer request remains open. Main asks the Utility Process to reconcile on macOS resume and unlock; reconciliation safely restarts both still-present execution children and active drafting children, avoiding falsely live but stalled post-sleep processes. If the Utility Process crashes, Main restarts it; startup reconciliation reactivates every durable queued, running, or waiting Analyzer/Solver execution before accepting new work.

After a terminal record is durable, the application automatically releases successful read-only Analyzer workspaces. It releases failed or cancelled workspaces only when `retainFailedWorkspaces` is disabled and preserves successful Solver/revision workspaces as implementation artifacts. Recovery applies the same decision and retries eligible cleanup. The Settings action may explicitly remove all inactive recorded workspaces after confirmation, while queued, running, and waiting owners are always skipped. Workspace cleanup and distributed claim cleanup are independent: removing a worktree never deletes a shared claim.
