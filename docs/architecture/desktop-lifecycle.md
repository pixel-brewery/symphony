# Desktop lifecycle

Everything Symphony persists lives in its configuration root, `~/.symphony` unless `SYMPHONY_CONFIG_ROOT` overrides it. Before the single-instance lock is acquired, Main relocates Electron's user data, session data, crash dumps, and logs into that root, so Chromium caches, cookies, and storage no longer accumulate in the platform's application-data directory and two configuration roots no longer compete for one lock. The previous platform location is remembered only to migrate an older database. Two deliberate exceptions remain outside the root: provider credentials belong to the `gh`, Codex, and Claude CLIs and to the operating-system keychain, and a Git worktree registers itself in the repository it belongs to.

After `app.whenReady`, Main installs the response-header security policy, resolves the configuration root, migrates the former application-data database when necessary, forks the Symphony background Utility Process with the configuration and state paths, registers the request handlers, and creates the main BrowserWindow. Development loads only the explicit local Angular URL; production loads the packaged file. New windows and unexpected navigation are denied. Settings has no window of its own: the application menu's **Settings…**, the menu-bar panel and `settings.open` show the main window and send it `/main/settings`; see [Settings in the main window](window-and-navigation/settings.md).

On macOS the main window uses a transparent window background with native sidebar vibrancy, keeps the traffic lights inside the 52 px sidebar header row, and the preload marks that capability with `data-native-vibrancy` without exposing Node.js or Electron APIs. On Windows and Linux the main window is frameless and keep their native window controls as a 52 px Window Controls Overlay at the right of the toolbar, painted in the Soho background and foreground roles of the current system appearance. The window chrome contract is described in [Window chrome and navigation](window-and-navigation/README.md#plattformrahmen).

Main pipes child output with a component prefix for local diagnosis, correlates requests, and rejects pending work if the child exits. It supervises and restarts an unexpectedly terminated Utility Process; the restarted service reconciles persisted active work before it accepts new work. macOS resume and unlock events trigger an additional typed reconciliation request so work interrupted by sleep or a network transition is reactivated without requiring the window to be opened. That reconciliation safely terminates and restarts still-registered pre-sleep Analyzer, Solver, and Work Item Creator children, so a stalled process cannot remain falsely active after wake. Durable executions resume their saved provider session; the still-open Work Item Creator request is regenerated from the same validated request and fresh tracker metadata. The same startup and lifecycle reconciliation invokes the disabled-by-default remote GitHub automation inbox, which catches changes received while the Mac slept or the application was stopped. Its normal interval runs in the Utility Process and is independent of renderer visibility. Symphony holds the operating-system single-instance lock. macOS activation or a second launch on another platform shows and focuses the existing main window rather than starting a competing background service.

The same Utility-Process schedule scans opted-in operational CI bindings when agentic delivery is enabled. A Utility Process crash or application restart reconciles the durable agentic journal with persisted executions and later workflow attempts before starting new work. A powered-off or suspended Mac cannot execute Actions follow-up; launch, resume, and unlock perform catch-up without retroactively acting on the activation baseline.

Application quit is a coordinated lifecycle operation. Main first requests the Zod-validated list of in-process Analyzer, Solver, revision, and Work Item Creator operations from the Utility Process. With none active, Main terminates the Utility Process and exits. With recoverable Analyzer or Solver work, a native warning offers **Keep running in background**, **Quit and resume later**, **Cancel tasks and quit**, and **Don't quit**. Background mode prevents process exit and hides the main window, so the same Main, Utility Process, bound agent children, event stream, and cancellation handles remain alive. Quit-and-resume sends a distinct pause signal, terminates the live agent child, durably retains `waiting`, and exits only after the Utility Process acknowledges that safe handoff; the next launch resumes the saved provider session. Cancel-and-quit instead persists the user's terminal cancellation. An active Work Item Creator request is not yet a durable execution, so its warning deliberately omits quit-and-resume and offers background continuation, cancellation, or no quit. If active work cannot be verified, paused, or cancelled, the safe default is not to quit; force quit remains an explicit operator override. The warning is native rather than renderer-owned because the renderer window may already be closed when the operating system requests application termination.

Background continuation protects normal user-initiated quit flows. A process or operating-system crash stops the live child processes, but it no longer loses durable Analyzer or Solver work: the next supervised Utility Process or application launch reopens the managed workspace and resumes the persisted Codex session. The macOS status item remains attached to that same application process and projects current agent and CI run evidence; a separately reconnectable operating-system daemon and native completion notification remain future capabilities.

Before the background service reports ready, it reconciles persisted queued, running, or waiting executions left by a previous process. It marks them `waiting`, validates the managed workspace, reconstructs the execution from its durable task snapshot, and resumes the saved provider continuation. Missing continuations fall back to a fresh Codex session in that same workspace. The renderer therefore presents an explicit recoverable state instead of either inventing live work or turning an infrastructure interruption into a failed task.

Packaged macOS and Windows applications also start the Main-owned update coordinator. It reads only the compiled HTTPS update origin and the validated machine-local Stable or Canary selection, checks after startup and periodically, downloads and verifies an available installer only on the person's request, and publishes bounded update states, including download progress, through the typed preload to every renderer window. Application shutdown aborts a running installer download and removes its partial file. A downloaded update never forces an active run to stop. Update installation first reuses the lifecycle-wide active-operation inspection: recoverable executions may be paused, transient drafts require explicit cancellation, and an unverifiable state defers installation. Main marks the quit as confirmed before launching the verified installer and quitting, or before delegating to Electron's native installer, so Utility Process supervision cannot race application replacement. See [Desktop updates](application-updates/README.md).
