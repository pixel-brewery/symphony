# Domain model

`WorkspaceDefinition` is the strict ownership boundary. `WorkspaceViewScope` is a display selection over one or more Workspace Definitions. `ProviderConnection` is workspace-owned and discriminated as Azure DevOps, GitHub, Codex, Claude, or OpenCode. An optional OpenCode connection may name one HTTPS OpenAI-compatible gateway; the gateway is still only one route behind that workspace account and never becomes a second global control plane.

`WorkItemSource`, `RepositoryBinding`, and `CiBinding` represent independent delivery capabilities. `PositionDefinition` describes company responsibility, required capabilities, write authority, path boundaries, diff limits, and implementation-iteration budget. `AgentProfile` identifies one enabled AI employee filling a position. `ProviderCapabilityManifest` declares one workspace provider/runtime protocol, capability set, and model-discovery mode without credentials. `AgentRoutePolicy` holds that employee's eligible account/model candidates, quality signal, hard cost boundary, affinity, and concurrency policy. `AgentTeam` assigns every delivery phase to a primary agent, explicit fallback agents, and one skill. `DeliveryContext` composes only same-workspace bindings and selects the team and default repository used by a task. Configuration validation rejects unknown IDs, duplicate IDs, undeclared provider capabilities, provider-kind mismatches, cost-policy violations, unsupported position roles, and every cross-workspace reference. A `free-tier` candidate additionally requires operator-approved, timestamped terms evidence that commercial use is allowed; otherwise the route is invalid.

`WorkItem` is provider-neutral tracked work with workspace/source identity, provider revision/native state, common editable content, repository binding IDs, labels, assignees, and an optional assistance action. `None`, `Create`, `Analyze`, and `Solve` are actions, not execution states. `CiRun` is a provider-neutral pipeline run. Neither exposes provider API documents.

`WorkTrackingProjection` and `ContinuousIntegrationProjection` are versioned, scope-owned read models for remote state. `RemoteDataStatus` distinguishes `current`, locally restored `stale`, and first-sync `unavailable` data, carries the last successful refresh time, and may name the safe recovery category `authentication-required`. Provider response bodies, exception messages, and credential values never cross this boundary. These types make provider failure actionable without allowing GitHub or Azure DevOps response types into application, persistence, IPC, or renderer boundaries.

`ExecutionRecord` captures one manual or AI analysis, solution, or revision. It owns a `workspaceId` and durable `ExecutionBindingSnapshot`, work-item snapshot, execution worktree/reference, provider continuation, attempt, state, summary/error, and timestamps. The binding starts with the planned delivery role, team, position, agent, route policy, route candidate, account, model, and reasoning level, then changes atomically before an explicit route handoff so a terminal record freezes the candidate that actually completed or failed last. A coordination-capable execution additionally owns an opaque `WorkItemClaim` with its action, provider-resolved owner, acquisition time, and eventual release time. `ExecutionEvent` is the ordered provider-neutral audit stream.

`GoalRecord` is the durable outer loop for one delegated work item. Its `WorkItemAgentAssignment` separates the accountable AI employee from the agent currently executing a phase. A successful Analyzer freezes an immutable, versioned `ImplementationContract` with instructions, acceptance criteria, allowed and forbidden paths, command policy, and change budgets. Every route or agent change can append a `HandoffSnapshot` while retaining the exact managed worktree. Solver completion appends a `GoalVerificationReport` containing changed files, diff size, contract-scope evidence, and repository-defined deterministic checks. The goal may enter `reviewing` only after those checks pass, and reaches `achieved` only through an explicit `GoalReviewDecision`; an agent's success message alone can never complete the goal. Revision feedback returns the same goal to implementation under the configured iteration limit.

`AgentPhaseAssignment` maps `work-item-creation`, `analysis`, `solution`, CI diagnosis/repair, or pull-request review to an exact portable package and accountable agent. Skills influence execution knowledge, never provider selection, permissions, state transitions, or isolation.
