# Provider model

The domain does not have a single generic “provider.” It has separate ports for work tracking, source control, CI, agent runtime, Git workspace management, persistence, and credentials. A provider type cannot cross another boundary: Azure DevOps response types stay in its adapter, GitHub API types stay in the GitHub adapter, and Codex, Claude, and OpenCode event formats stay in their runtime adapters.

| Capability             | Production adapter                                | Workspace-owned configuration                                                              |
| ---------------------- | ------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| Work tracking          | `AzureDevOpsWorkTracker`, `GitHubProjectTracker`  | Azure query binding or GitHub Project owner/number, connection, and status-column mappings |
| Work-item coordination | `GitHubProjectTracker`                            | authenticated contributor, Project, repository/default branch                              |
| Source control         | `GitHubCloudProvider` plus local Git              | host, explicit account login, owner/repository/default branch                              |
| CI                     | `GitHubCloudProvider`                             | repository-scoped GitHub Actions binding                                                   |
| AI                     | `SynapseAgentRuntime` through `SynapseAiService`  | team phase, agent route, account-bound credential source, model                            |
| Execution files        | `GitWorktreeWorkspace`                            | repository binding and per-workspace execution root                                        |
| Repository acquisition | `ManagedGitRepository`                            | GitHub identity and workspace-owned managed clone root                                     |
| Local verification     | manifest planner plus `LocalVerificationExecutor` | machine-local capabilities, commit-pinned plan, isolated runtime home                      |
| Feedback intake        | `MicrosoftTeamsFeedbackIntake`                    | tenant/app, team/channel, credential reference, GitHub target                              |

`AzureDevOpsWorkTracker` reads saved queries or WIQL, hydrates work items in bounded batches, maps process-specific states through Azure DevOps state categories, and uses revision tests for optimistic updates. A person pastes a PAT once in the Azure DevOps source editor. Electron Main encrypts it with the operating system's secure-storage backend (the login keychain on macOS), persists only the encrypted blob, and synchronizes the decrypted value into Utility-Process memory after every background-service start. Application settings retain only a connection-bound `vault:azure-devops:<connection-id>` reference; the broker refuses a vault reference belonging to another connection. `env:` PAT and `entra-env:` access-token references remain supported for unattended and migrated installations. The renderer never receives a stored credential, and workspace exports omit every credential reference.

`GitHubProjectTracker` discovers Project V2 field definitions and exhaustively paginates Project items and nested item connections through GraphQL. A page size of 100 and bounded query batches are transport controls only: pagination continues until `hasNextPage` is false, so no board item, field value, label, assignee, or coordination claim is functionally capped. The board projection contains the complete item set with summary fields; issue body and remaining detail are hydrated through a dedicated provider operation only when a ticket is opened or before execution. Text, number, date, single-select, multi-select, and iteration fields are projected into the provider-neutral field model and written through typed mutations. `Assistant phase` is recognized as the assistance-action role. The adapter also implements `WorkItemCoordinationPort` with an atomic repository ref and returns only the opaque provider-neutral claim; GitHub ref and commit payloads do not cross the boundary. Issue content remains owned by GitHub Issues. Remote automation uses repository issue and comment feeds with the durable source checkpoint as `since`, then hydrates only changed board issues, validates the configured account actor, and emits provider-neutral signals for the [remote automation](remote-automation.md) inbox. `WorkTrackerRouter` selects and aggregates both production adapters from workspace-owned work-item sources without allowing GitHub GraphQL types to cross the adapter boundary.

Relationship evidence for delivery-group proposals is produced by the separate `WorkItemRelationAssessor` adapter: it runs the workspace's active Analyzer skill read-only against the repository binding's ordinary local checkout (no isolated worktree is prepared), is bounded by a timeout, and reduces every failure — no active Analyzer skill, no local checkout, a failed run, an unparsable verdict — to the neutral `unrelated` assessment, which never satisfies the delivery-group activation gates. Simulated agent mode does not bind this adapter and keeps the application service's deterministic lexical relation heuristic instead.

For provider-neutral relationship evidence on the tracker, the GitHub adapter idempotently maintains `grouped-delivery` and `critical-path` labels and one HTML-marker-owned comment per issue. The comment names the target root, members, current state, shared change surface, and shared pull request when available; dissolution updates that marker and removes the active label instead of adding a contradictory comment. Delivery publication supplies a separate `Resolves` line for every group member while leaving issue bodies and identities unchanged.

The GitHub Project and GitHub Cloud adapters share one process-wide request governor. It bounds concurrency, observes GraphQL cost/remaining/reset metadata, fails fast while a known exhausted window is active, and lets the background scheduler resume at the reported reset or an exponential retry. Startup completes the initial background reconciliation before recurring GitHub jobs begin, and identical in-flight projection/detail reads are coalesced. These controls regulate request timing, never result cardinality.

`GitHubCloudProvider` uses the GitHub CLI as credential broker but passes the token for the connection's explicit host/account into each API subprocess. It does not rely on whichever GitHub account happens to be globally active. Account identity comparison is case-insensitive, while token lookup uses the exact login spelling reported by GitHub CLI. It exhaustively lists open pull requests for every enabled GitHub repository in the selected workspace scope and projects only provider-neutral identity, title, author, draft, branch, time, URL, and base-relationship fields. The base relationship is reduced from GitHub's mergeability metadata to `current`, `behind`, `conflicting`, or `unknown`; entries GitHub is still computing are hydrated through bounded per-pull-request detail reads and otherwise remain `unknown` instead of being guessed. This collection is independent from Symphony execution history. The adapter also updates one pull-request branch on request — for a listed row after re-reading the pull request and refusing a closed, merged, conflicting, or still-calculating branch, and through the delivery port for the autonomous cycle, which additionally refuses the repository default branch. Both paths call GitHub's update-branch operation with the exact observed head as the expected-head precondition, so GitHub creates the merge commit and rejects a concurrently moved head; the adapter never rebases, force-pushes, or merges. The adapter separately lists GitHub Actions runs and exposes named cancel/rerun operations. For an explicitly selected queued workflow it may obtain a short-lived repository runner token and delegate execution to the [managed local CI](managed-local-ci.md) adapter. Repository content, Git operations, and VM lifecycle remain separate from GitHub API payloads.

The same adapter reads the current GitHub Actions billing month for an explicitly bound repository account through GitHub's consolidated billing API. It projects only provider-neutral used, included, remaining, percentage, account, and reset metadata. Included-minute derivation is limited to GitHub Free, Pro, and Team plans and to the standard hosted-runner SKUs that consume those allowances; larger-runner usage is excluded. Plans whose account-wide allowance cannot be proven from the repository account response, including enterprise arrangements, expose used minutes without inventing a remaining value. Owner or billing-manager authorization failures become bounded usage errors and never masquerade as zero remaining minutes. Usage is live operational state and is not persisted.

Symphony delegates technical CLI execution, native authentication, process ownership, session binding and generic routing primitives to the separately maintained `@pixel-brewery/synapse-*` packages. `SynapseAgentRuntime` retains the analysis, implementation and issue-drafting prompts and translates provider-neutral events/errors into existing application ports. `SynapseAiService` composes the three native drivers, one runtime and the shared auth gate in the orchestrator. GitHub authentication and developer-tool installation remain Symphony-owned. No CLI execution moves into the renderer or Electron Main.

Profiles preserve the existing workspace/connection paths and settings identifiers. Login, logout, explicit account import and changed credential configuration block new work and drain affected native processes before mutation. Complete versioned continuation references fit existing opaque SQLite fields and retain their original authentication generation; legacy native IDs remain usable until the first account/configuration transition. Persisted generations reject old sessions after an account switch or restart. Native credential refresh preserves the generation. Routine status checks never initiate login or inference.

Symphony configures the shared runtime with its maximum supported native timer window (2147483647 milliseconds, about 24.8 days) so ordinary long-running turns retain their existing behavior; callers can supply a shorter explicit per-request deadline. Cancellation and Utility Process shutdown await owned process cleanup. Metadata and authentication have separate bounded lifecycles. This supplies a finite native timer ceiling for the original unlimited-duration adapter assumption in ADR-003; the library's general thirty-minute default does not apply to Symphony. Native CLI compatibility is characterized through sanitized synthetic protocol replays; regular CI needs no personal account, and live-account checks remain explicit.

Symphony consumes the seven required libraries as exact `0.0.1` dependencies from the `@pixel-brewery` GitHub Packages feed. The existing Yarn scope configuration supplies registry authentication through `GITHUB_TOKEN`; no local archives, source aliases or developer checkout paths are required. The lockfile records the registry artifacts and their transitive dependencies. ACP, test fixtures and the documentation MCP remain optional packages outside the production consumer.

`WorkspaceAgentRuntime` chooses Codex, Claude, or OpenCode from the executing phase's workspace-owned team assignment and agent route. Analysis, implementation, work-item creation, CI repair, and review can therefore use different positions, agents, accounts, models, and cost policies without crossing a workspace boundary. Provider manifests and position requirements filter candidates by declared capability before execution. Candidate order is derived within each agent from `priority`, `quality-first`, `last-known-good`, `lowest-cost`, `lowest-latency`, `most-reliable`, `least-used`, `reset-aware`, or `balanced`; the team's explicit fallback-agent order remains authoritative around those per-agent choices. `balanced` compares consecutive failures, marginal-cost class, observed average latency, and configured priority in that order. Every assignment progress event includes the selected strategy, cost class, quality, observed reliability, and latency so a handoff is explainable without exposing provider payloads. Explicitly repeatable read-only work may advance to the next candidate after a retryable provider failure. Implementation stops after a started attempt: it is never automatically replayed on a backup. Cancellation, host/progress persistence failures, invalid results and explicit test failures do not trigger a handoff; host failures do not count against provider health.

The route governor writes attempt, success, failure, latency, last-success, and cooldown data to the executing workspace's `state.sqlite`. Two consecutive failures open that candidate's circuit for five minutes; repeated failures also contribute to the declared provider's workspace-scoped circuit, so a broken upstream can be bypassed across multiple accounts without affecting another provider or workspace. Open candidates are skipped, an expired cooldown admits a half-open probe, and an entirely cooling-down pool fails fast with an explicit retry time. A successful probe closes the relevant circuit. A temporary telemetry-write failure is logged and falls back to process-local route memory; it can never turn a successful provider result into a duplicate failover execution.

Account capacity is a separate routing layer from candidate health. Codex and Claude CLI rate-limit responses, plus explicit Codex, Claude, or OpenCode account-quota exhaustion, create one cooldown keyed by workspace and AI connection. The originating call records candidate telemetry without degrading the provider-wide circuit, and every later candidate using that account is skipped before model inspection, admission, or provider invocation; candidates backed by other accounts remain eligible. Ambiguous OpenCode `429` responses are not promoted to account scope because one OpenCode connection can expose independent upstream model providers. Explicit retry/reset timestamps are honored with a 31-day safety cap; otherwise rate limits cool for one minute and exhausted quotas for fifteen minutes before a probe. The cooldown contains only reason and timestamps, persists in the workspace's `state.sqlite`, and is cleared by relevant settings, authentication, and workspace changes. Persistence failure keeps in-process protection without causing a duplicate provider call.

`maxParallelExecutions` is enforced by an in-process admission queue keyed by workspace and route policy, so candidates of one agent route share its declared capacity without consuming another workspace's slots. Queued work remains cancellable, waiting time is excluded from provider latency and attempt telemetry, and the candidate circuit is checked again after admission. Capacity is released before success or failure is returned to the caller, preventing an immediate fallback from observing a stale occupied slot. Queue state is intentionally ephemeral: durable execution recovery owns interrupted work, while process-local admission owns only currently running provider processes.

An explicit candidate model is checked before queue admission only when its provider runtime reports an authoritative account-scoped model list. Codex uses the same isolated app-server response as its account settings. OpenCode uses `opencode --pure models` with the exact workspace/account runtime home and inline configuration used for execution; Symphony has no independent provider or model inventory. A runtime response that positively omits the model locks out only that account/model candidate and proceeds to the next route without recording a provider attempt or failure. Available evidence is cached for five minutes, unavailable evidence for one minute, and an inspection failure or empty response remains `unknown` for fifteen seconds and fails open. Cache keys include workspace, account, and model and are cleared on relevant settings, authentication, and workspace changes. Claude Code has no supported non-interactive model-list command, so Claude candidates remain `unknown`; the operator may leave the model empty for the account default or pass an exact alias/identifier to the CLI without Symphony inventing availability.

Provider-specific continuation state is retained only when the persisted execution binding names the exact route candidate and that route enables session affinity. It is cleared before every other route or agent receives the task, while an explicitly resumed implementation retains its isolated worktree and approved analysis so partial local evidence is preserved. The durable execution binding is updated before every attempt and therefore identifies the route candidate, agent, account, model, and reasoning level that actually owns the current run. Route candidates are evaluated fail-closed; a `free-only` or `local-only` policy never broadens its pool when no eligible candidate exists. Every Codex connection receives a connection-specific credential home. On upgrade, a former user-home connection copies the existing `auth.json` once into that home and is persisted as isolated, so the current login survives without remaining shared. Before execution, Synapse snapshots only that account's `auth.json` into its application-owned runtime home and gives Codex separate application-owned `HOME`, temporary, SQLite, session, and configuration paths. Refresh persistence compares the original credential baseline and fails explicitly on conflicting changes; Windows uses ordinary private files. Ambient user configuration and exec-policy rules are ignored. CLI session overrides reassert the phase sandbox, disable hooks, plugins, apps, browser/computer access, multi-agent execution, notifications, bundled skills, and every MCP server declared by the target repository. The credential source is persisted on the connection and is never inferred from display names or another account's authentication state.

The implementation contract and handoff snapshots are the context-compression boundary: later, cheaper agents receive the bounded objective, acceptance criteria, scope, verification evidence, and same worktree instead of an unconstrained transcript. Durable successful analysis is reused by the same goal; Symphony deliberately does not semantically cache model answers or replay writes, because an inexact cache hit could bypass current repository evidence or execute a mutation twice.

Claude subscription login, status, logout, and execution use the same connection-specific `HOME` and `CLAUDE_CONFIG_DIR`. Claude Code documents this configuration override for running multiple accounts side by side; Symphony gives every workspace account a different directory instead of reading the Claude desktop app or another workspace's active login. On macOS Claude Code keeps OAuth credentials in the login keychain under a service name hashed from `CLAUDE_CONFIG_DIR` (Symphony pins that through `CLAUDE_SECURESTORAGE_CONFIG_DIR`), so accounts stay separate there too. Because `security` locates the login keychain through `$HOME/Library`, the isolated home links `Library/Keychains` and `Library/Preferences/com.apple.security.plist` to the user's real ones; without that, credential writes land in the System keychain and macOS shows an administrator prompt from an "unknown" application. The browser authorization URL is opened by Electron Main; an optional authorization code crosses the validated IPC boundary once and is written only to the active Claude CLI process. An `ANTHROPIC_API_KEY` may instead be resolved from the connection's environment credential reference. Symphony communicates with coding agents through isolated CLI adapters. It owns workspace account credentials, routing policy, and failover, while each CLI remains authoritative for its supported models. OpenCode remains an optional isolated coding-runtime adapter for compatible providers. It receives a connection-specific `HOME`, only the exact environment credential named by the connection, an inline application-owned configuration, and `--pure`; project configuration, ambient Claude compatibility, external plugins, subagents, external directories, commits, and pushes are disabled at the runtime boundary. Analysis is read-only, implementation is limited to the isolated worktree, and prompts forbid commits, pushes, merges, and external tracker mutation. Provider continuation IDs are persisted as opaque values inside the workspace-owned runtime home.

An operator may explicitly import the provider sign-ins currently stored by OpenCode on the Mac into one saved workspace account. The orchestrator copies only OpenCode's credential file into that account's isolated runtime home with mode `0600`; it never sends credential contents to the renderer. This is a point-in-time copy, not a link: later authentication changes in the global OpenCode installation or another workspace do not cross the workspace boundary. The isolated CLI then remains the sole authority for the provider/model identifiers exposed to that account.

OpenCode execution requires a separately installed CLI discoverable through `PATH` or a standard package-manager binary location. The executable inside `OpenCode.app` is the desktop UI and is never probed or launched as a CLI. Settings may install the separate CLI with the fixed `brew install anomalyco/tap/opencode` recipe after explicit confirmation; equivalent fixed recipes exist for the other supported developer tools, while arbitrary packages and arguments never cross IPC.

Simulated adapters are test-only implementations of the same ports. The simulated pull-request delivery adapter scripts its base-relationship observations through `SYMPHONY_SIMULATED_PR_BASE_STATUS` — a comma-separated sequence of `current`, `behind`, `conflicting`, and `unknown` consumed one observation per inspection, with the last entry repeating — and mirrors the production update-branch parity: the update requires the exact expected head observed before it and forces the next inspection of that pull request to `current`.

Repository acquisition, project inspection, verification planning, approval persistence, and execution are separate ports. GitHub credentials end at acquisition; verification receives no provider or AI credential. The typed plan is created in the Utility Process and the renderer can approve only its opaque ID. See [Local repository verification](local-repository-verification.md).

`MicrosoftTeamsFeedbackIntake` uses an application token and the team-scoped Microsoft Graph `ChannelMessage.Read.Group` permission to read one configured channel. It recognizes FLAMOX365 feedback Adaptive Cards and explicit `@Symphony` requests, then emits provider-neutral feedback signals. The [feedback intake application service](teams-feedback-intake.md) owns baseline, deduplication, Work Item Creator drafting, and tracker creation; Microsoft Graph types and credentials do not cross the adapter boundary.
