# IPC model

Feature packages under `libs/ipc-contracts/features` own the existing method schemas. `@symphony/ipc-contracts-composition` composes the 115 orchestration methods; `@symphony/ipc-contracts-desktop` owns the 15 native methods. Core owns shared envelopes and events. The request map, response map and discriminated request envelope retain their three historical method orders and the original schema instances, defaults and transformations. The split changes ownership and public exports, not the wire protocol.

`runtime-dependencies.install` is the narrow developer-tool installation action. It accepts one enum value rather than a command or package string; the Utility Process owns the fixed Homebrew recipe and returns the refreshed validated health projection.

OpenCode follows the existing provider event boundary: raw JSON events remain in the provider adapter and only the bounded provider-neutral projection crosses IPC.

One fixed invoke channel carries background-service request envelopes and one fixed pushed channel carries execution events. A separate named native-path channel opens the operating-system file or directory dialog. The method union covers health/snapshot reads, manual and AI Analyzer/Solver completion, per-execution pause, resume, and cancellation, narrow autonomy status and enablement, lifecycle reconciliation, lifecycle-wide active-operation inspection, pause, and cancellation, managed-workspace cleanup and workspace transfer, work-item editor metadata, Issue create/update/draft/cancel operations, settings, connection status, GitHub login/logout, and Codex login/logout. Pushed execution events may carry only provider-neutral origin and stream-category metadata beside their bounded visible message; raw Codex JSONL and OpenCode JSON events never cross the process boundary. `analysis.complete-manually` and `solution.complete-manually` accept a work-item ID plus bounded Markdown and never resolve a skill or start an agent. `analyzer.start` requires a work-item ID and accepts an optional bounded focus prompt that is persisted on the execution and passed to the assigned analysis skill. `solver.start` requires a work-item ID and accepts a bounded feedback string for AI revisions. `analyzer.start` and `solver.start` return an admission rather than a run: either the started execution, or the durable queue entry created because every execution slot was taken. `execution-queue.remove` withdraws one waiting step by its entry ID and returns the removed entry. `snapshot.get`, `snapshot.refresh`, and `execution-state.get` carry the queue beside the executions, so every surface reads the same waiting steps. `execution.pause`, `execution.resume`, and `execution.cancel` address one execution by its durable ID. `autonomy.status.get` exposes only enablement, capacity, and the next scheduled cycle; `autonomy.set-enabled` changes only the autonomous-work flag rather than accepting the broad settings document. Main invokes `lifecycle.reconcile` after macOS resume and unlock; the orchestrator only reactivates persisted active records that have no live owner in that Utility Process. `lifecycle.active-operations.get` reports only the provider-neutral identifiers and kinds of operations owned by the current Utility Process. `lifecycle.active-operations.pause` interrupts Analyzer and Solver children while retaining durable `waiting` state for a later launch; `lifecycle.active-operations.cancel` aborts and awaits every registered operation before acknowledging terminal cancellation and a safe quit. `workspaces.clear` has no path input: the orchestrator derives inactive candidates from its execution records, skips active owners, and returns validated cleanup counts. `workspaces.export` and `workspaces.import` accept only a workspace ID plus a native-selected destination, or a native-selected bundle file; the renderer never reads or writes bundle bytes. Import returns validated settings and bounded setup counts, and is rejected while the matching workspace owns active work. `work-items.create` and `work-items.update` accept the provider-neutral title/body/repository/state/labels/assignees mutation. `work-items.move` addresses one work item and one board column by their provider identifiers and changes nothing else; the tracker writes the column, and the workflow record adopts the resulting stage exactly as it does for a card a person moves in the tracker itself. `work-items.comment` addresses one work item plus one bounded Markdown body: the tracker writes the comment into the provider discussion, and the method answers with the complete item whose thread now carries it, so the drawer that reads a discussion can also answer in it. A provider that carries no discussion refuses the comment with that reason instead of dropping what was written. `work-items.draft` is the explicit AI branch: it accepts a client-generated operation ID plus bounded free-text context and returns a Zod-validated title, Markdown body, provider-neutral state, labels, and assignees. `work-items.draft.cancel` addresses that transient operation ID. The orchestrator supplies the current tracker metadata to the Creator and rejects every returned classification value outside that allowlist before it crosses back into the renderer. Every envelope includes a correlation ID; method-specific payload and response schemas are defined with Zod in `libs/ipc-contracts`.

`snapshot.get` returns the current complete provider-neutral board projection, normally from the fresh local materialized view, while `snapshot.refresh` explicitly rebuilds it from every remote page. Neither method accepts a result limit. Board items carry only a validated summary/detail state; `work-items.detail` addresses one item ID and returns its hydrated provider-neutral detail, including the provider discussion thread (`comments`, oldest first) that a summary never carries. The renderer invokes that narrow method when the edit/detail drawer opens, while Analyzer, Solver, and manual execution paths invoke the same application operation before starting so summary data can never become execution input.

`codex.configuration.get` is the bounded metadata read for one explicitly addressed workspace-owned Codex account. Its validated response contains the models reported by the Codex app-server, each model's supported reasoning efforts, current rate-limit windows, and optional aggregate token statistics; credentials and raw app-server payloads never enter the renderer. `ai.models.get` applies the same boundary to OpenCode by returning only the provider/model identifiers emitted by `opencode --pure models` for one workspace-isolated runtime home. Explicit account identity prevents an aggregate workspace view or a globally active CLI account from leaking model access or usage between customer accounts.

`ci.usage.get` is the bounded live-usage read for one to 100 explicitly addressed repository bindings. Its response is keyed by repository binding and contains only provider-neutral account, billing-period, minute, percentage, and bounded error metadata. Credentials, raw GitHub billing payloads, and unverified allowance assumptions never cross into the renderer. A missing `remaining` value means the allowance could not be derived; only an explicit validated value of zero may drive an exhausted-allowance warning.

`local-ci.images.list` returns the selectable GitHub runner image releases for this Mac's architecture together with the pinned selection of every workspace. The orchestrator reads the machine-readable catalog `actions/runner-images` publishes, caches it below the local CI runtime root, and serves the cached catalog with a bounded `staleReason` when the upstream refresh fails. `local-ci.image.select` resolves one release into a reproducible guest definition — Ubuntu cloud image and digest, declared apt package set, declared Node.js runtime and digest, exported environment — and persists it on the workspace. It is rejected while a managed run is active. Neither method accepts a URL, a package list, or a script from the renderer.

`ci.local.run` is accepted only while the machine-local Local CI setting is enabled, and the orchestrator serializes it to one managed VM. `ci.local.cleanup` accepts no renderer path; it derives the runtime root from validated settings, rejects cleanup during an active local run, removes only Symphony-owned instances, and then clears the inactive runner cache. Both request and response remain method-specific Zod contracts.

`storage.status.get` is a read-only, path-free renderer contract. The orchestrator measures allocation across application state, the bounded Electron browser profile, managed workspace repositories/worktrees/runtime homes, verification data, and Local GitHub Actions. Where the operating system reports a non-negative block count, it uses `blocks * 512`, including a valid zero allocation for a sparse file. If that metadata is absent or invalid, it retains the existing conservative logical-size fallback, `stat.size`; the result is not a promise of exact physical allocation on every filesystem or platform. It returns global, per-workspace, Local CI, and filesystem-reserve pressure without accepting a filesystem path from the renderer. A large-tree detail inventory runs cooperatively and may report that categorization is still in progress; admission independently checks live filesystem availability and reserves the workload's complete bounded growth instead of blocking on that inventory. Disk-writing methods are gated in the orchestrator, so hiding or bypassing the Settings UI cannot bypass a storage limit.

`ci.runs.refresh` is the narrow live-status path for the run surfaces: the main window's run panel and GitHub-sync **Retry** in the status bar, both through the CI feature's store, and the menu-bar panel. It refreshes only the provider-neutral CI projection and returns its remote-data status plus bounded local CI evidence; it does not reload work items or pull requests. The renderer validates the response before replacing only those snapshot fields.

`workflow.stage-changes.list` and `ci.runs.history.list` are the bounded history reads behind the Overview's `Reporting`. Both accept an optional configured `workspaceId` (otherwise every workspace of the active view scope; an unknown workspace is rejected) and an ISO `since` instant, and never accept a path, a limit or a query. `workflow.stage-changes.list` returns `{ changes: [{ workItemId, fromStageId?, toStageId, changedAt }], recordedSince?, truncated }`: every recorded stage change of each work item that changed stage at or after `since` (including that item's earlier changes), newest first, at most 10,000, with `since` clamped to the last 400 days. `ci.runs.history.list` returns `{ runs, recordedSince?, truncated }` with at most 10,000 recorded finished runs in the provider-neutral run shape, `since` clamped to the 200-day retention. `recordedSince` is the instant from which the list is complete — the earliest record of the scope, or the oldest returned record when the maximum cut the list — so the renderer can tell missing history from an empty period. See [Overview und Inbox](overview-and-inbox/README.md).

`pull-request.branches`, `pull-request.compare`, and `pull-request.create` are the operator-authored pull-request path, separate from `pull-request.publish`, which delivers an execution's managed worktree. All three address one repository binding that must be enabled, GitHub-backed, and inside the selected workspace scope; the Utility Process resolves owner, host, connection, and token itself and never accepts a URL, host, owner, or credential from the renderer. `pull-request.branches` returns at most 1,000 provider-neutral branch names with their protection flag. `pull-request.compare` returns the provider-neutral comparison of one branch pair: status, ahead/behind counts, changed-file count, at most 20 recent commits, and the open pull request that already covers the pair. `pull-request.create` accepts the branch pair, a bounded title and Markdown body, and the draft flag, and returns the created pull request in the same summary shape the board projection uses. This path never commits, pushes, or merges: both branches already exist on the provider, and the renderer receives only the validated summary.

`ci.run.details` is the on-demand Action-log path. It accepts one provider-neutral run ID and returns at most 100 jobs with at most 1,000 bounded steps per job. GitHub job response types remain in the provider adapter; the renderer receives only validated names, statuses, timestamps, and optional external job URLs.

Preload exposes only:

```ts
request(method, payload): Promise<response>
selectPath(request): Promise<{ canceled, paths }>
onExecutionEvent(listener): unsubscribe
```

It never exposes `ipcRenderer`, Electron, direct filesystem access, tokens, API keys, or generic channel names. Main verifies the sending `WebContents` and validates native path-selection requests and responses. Background-service requests are revalidated and correlated with Utility Process responses. Short control requests retain a response timeout; the blocking Work Item Creator request deliberately has none and remains pending until the bound agent completes, fails, or the user sends its named cancellation request. Analyzer and Solver start requests return their durable execution immediately, so their agent runtime is never governed by the IPC response timeout. The Utility Process validates before dispatch and Main/Preload validate on return. Secret-bearing login payloads are never logged or returned. `azure-devops.login.start` is the sole renderer request that carries an Azure DevOps PAT; Main stores it through OS secure storage before forwarding the bounded request and rolls the encrypted value back when verification fails. `azure-devops.logout` removes both the in-memory binding and its encrypted blob. On Utility-Process startup Main sends only the validated opaque references backed by encrypted blobs. When the Azure DevOps adapter is about to use one connection, the Utility Process sends a correlated internal resolution request; Main returns that one secret or a secret-safe missing/unavailable result, and both sides validate the discriminated message contract. Unknown or malformed messages are not dispatched. Future log pagination will add named methods rather than generic IPC escape hatches.

A separate correlated desktop envelope owns Main-terminating operating-system capabilities. Its method union is limited to `updates.get`, `updates.check`, `updates.download`, `updates.channel.set`, `updates.install`, `window.show`, `menu-bar.resize`, `menu-bar.status.set`, `app.quit`, `power.get`, `power.keep-awake.set`, `speech.start`, `speech.stop`, `speech.cancel`, and `settings.open`, in that order, with exhaustive Zod-validated update and power states, speech-recognition events and navigation targets pushed on fixed event channels. The power methods carry a boolean preference only; Main derives the machine-awake assertion from the Utility Process's own active-operation count, so the renderer can never hold the machine awake by asserting that work exists. `window.show` accepts only `current`, `settings`, `actions`, `inbox`, `notifications`, or `new-work-item`; `settings` shows the separate Settings window, every other value shows the main window and, except `current`, sends the matching fixed navigation target to it. `settings.open` accepts an optional record of at most eight Settings location parameters with bounded keys and URL-unreserved values, opens or focuses the single Settings window, and navigates it there. Navigation targets are restricted to the closed `DesktopNavigationPath` allowlist that Preload re-checks before handing a target to the renderer; see [Settings window](window-and-navigation/settings-window.md). The menu-bar methods accept only a bounded integer height and the semantic `idle`, `running`, or `failed` mark state, so the renderer cannot pass arbitrary BrowserWindow options or native image paths. The Settings window and the hidden menu-bar renderer are trusted for this narrow desktop envelope and the orchestration envelope; native path selection is accepted from the main and Settings windows only and is attached to the requesting window. This contract never accepts or returns an update origin, URL, credential, path, arbitrary route, or arbitrary Electron option. `updates.download` starts Main's in-app download of the validated installer it retained and answers `started`; only when no in-app download can start does it open that retained URL externally (`opened`) or answer `not-available`. Download progress travels only as the bounded `progress` share of the pushed `downloading` update state. Native update installation may call the existing typed Utility Process lifecycle methods internally before Main performs the operating-system restart.
