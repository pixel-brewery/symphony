# Deployment and packaging

**Dokumentstatus:** Implementierter Ist-Stand

This page describes the implemented packaging, configured public release infrastructure and evidence required for each desktop publication. The complete update and publication contract is owned by [Desktop updates](README.md).

Nx builds Angular into `dist/apps/renderer/browser`, Electron Main and sandbox-compatible CommonJS preload into `dist/apps/desktop`, and the ESM Utility Process into `dist/apps/orchestrator`. Main resolves both renderer and child relative to its packaged module. Forge packages the repository with ASAR enabled and active platform makers for DMG, Debian, and Squirrel; the ZIP maker remains commented out for a later support expansion. The release pipeline selects ARM64 on every platform and publishes only the DMG, EXE, and DEB installer outputs. Forge always applies an ad-hoc macOS bundle seal without Hardened Runtime or notarization; Windows and Debian installers are unsigned. Platform certificate configuration is not supported.

## Cross-platform consumer build contract

`yarn design:md` and `yarn design:md-check` use the installed public
`mosaik-design-md` CLI from `@pixel-brewery/mosaik-themes` version `0.1.199`.
Its configuration serializes repository-relative source paths into the generated
Markdown headers. The upstream CLI uses native path separators there, making a
Windows check report the committed `DESIGN.md` as stale even when the theme and
component values are unchanged. This CLI version exposes no public path-header
normalizer option.

The native Yarn patch
[@pixel-brewery/mosaik-themes 0.1.199](../../../.yarn/patches/mosaik-themes-0.1.199-path-separators.patch)
changes only `config.where` in `bin/design-md.mjs`: its relative display path
replaces backslashes with `/` before rendering Markdown. It does not change
filesystem resolution, theme evaluation, component APIs or runtime styling.
The existing generator and stale-output check remain authoritative; committed
`DESIGN.md` and `COMPONENTS.md` must remain byte-for-byte unchanged by this
portability correction.

The committed patch, central [Yarn resolution](../../../package.json) and
[lockfile](../../../yarn.lock) are one dependency contract.
`yarn install --immutable` selects and applies the patch from that contract;
manual edits to `node_modules` and a parallel generator wrapper are not part of
the build. All direct Mosaik family versions remain pinned to `0.1.199`, with
no upstream release or runtime/component patch introduced by this correction.
The [design CLI policy regression](../../../tools/design-md-portability.policy.spec.ts)
invokes the actual installed CLI with native and Windows-style path serialization
and compares its outputs and unchanged document bytes. A simulated separator
check is not evidence of a completed Windows CI run or a desktop release.

Remove this consumer patch only during a coordinated Mosaik upgrade after the
upstream CLI supplies the same platform-independent header behavior. Update the
resolution and lockfile together, and require the actual design checks on both
Windows and a POSIX platform to pass with unchanged reviewed design documents
before accepting removal. A matching package version alone does not establish
that the upstream fix exists.

## Native application assets

The canonical Symphony mark and every generated application-icon format live under the top-level `resources/icons` directory. `yarn icons:generate` derives browser PNGs, menu-bar templates, and the native ICNS and ICO containers from that mark. Renderer and mobile builds copy their icons from the same directory, Electron Main uses its packaged resource copy for the window and macOS Dock icon, and Forge uses the native files for macOS, Windows, Debian, and installer metadata. Publication retains each version's ICO as a GitHub Release metadata asset and reproduces it beside the version manifest on the update origin so Squirrel can resolve the Control Panel icon without depending on the source repository. The public download page uses the same branded resource family.

Every macOS launch explicitly sets the Dock image from the active application's resources, including packaged builds. This prevents a same-name local rebuild from relying on an older icon retained by the operating system. Replacing a bundle on disk does not update the image already held by a running process; the new process applies the current image at startup. This image refresh keeps the established bundle identity and does not clear global operating-system caches.

The menu-bar templates use a 24-point canvas with 48-pixel Retina representations. The posthorn uses its full geometry without an additional inset; running and failed badges occupy the free space above its right arm. All three states preserve the same posthorn size and alignment, and badges do not obscure the mark. Native visual acceptance checks the rendered menu-bar size and the packaged Dock image as well as the generated files.

`yarn start` builds and launches the platform's packaged Symphony application so operating-system surfaces use the branded bundle name and icon. `yarn start:unpackaged` and `yarn dev` retain Electron's raw development bundle for diagnostics and live development; macOS identifies that upstream bundle as Electron in the Dock.

`yarn package:smoke` performs a production build, runs `electron-forge package`, then verifies the unpacked application contains the expected executable bundle and renderer assets. The desktop release workflow prepares one semantic Nx Release version for each `main` change outside the documentation-only allowlist or an explicit manual release request. Documentation-only automatic pushes stop before candidate preparation, verification and native builds; the [repository-quality contract](../repository-quality/README.md) defines the exact comparison and exclusions. Verification, all native builds, and publication use the same metadata-only commit, transferred through an internal Git bundle. The workflow uses a complete ad-hoc macOS bundle seal and intentionally unsigned Windows and Debian installers. No certificate material is imported or passed to Forge, and notarization is not supported. Hardened Runtime stays disabled because the ad-hoc identity has no stable Team ID for library validation of the embedded Electron Framework. The workflow unconditionally verifies the strict ARM64 macOS bundle signature, requires its ad-hoc identity, rejects the runtime flag, verifies its DMG, and whitelists exactly one ARM64 installer per platform before upload. After the final source-revision check, it atomically pushes the version commit, changelog, and tag, then publishes and verifies the GitHub Release with its immutable installer and metadata assets. A dependent Actions workflow reconstructs and deploys the download site and channel manifests from those retained Releases; it does not commit generated folders. The Debian package remains unsigned and requires no signing credential. Native automatic-update feeds remain unchanged while their commented ZIP and NuGet payloads are disabled; installer-only releases are detected in-app and replaced manually. Review the public source and manifest checksums before downloading or running at your own discretion; the [MIT license](../../../LICENSE) provides the software as-is, without warranty. The complete publication layout, GitHub Actions configuration, runtime lifecycle, and recovery policy are defined in [Desktop updates](README.md).

### macOS disk-image installation and first launch

The DMG contains the packaged application, an `/Applications` symlink and a passive UTF-8 text guide, `Read me first - Open Symphony.txt`. The guide is a packaging asset under `resources/macos`, not executable application code. `MakerDMG.contents` uses its public callback's `appPath`, retaining the application's default position at `(192, 344)` and the destination at `(448, 344)`. The guide appears above both at `(320, 120)`. The existing default arrow background remains in use; the public `additionalDMGOptions.window.size` is `658 × 498` so every entry is visible without scrolling. Providing custom contents replaces the maker's defaults, so the app and destination are explicitly retained.

The guide explains copying the app into Applications, trying that copy once, dismissing a developer-verification block with **Done**, and selecting the app-specific **System Settings → Privacy & Security → Open Anyway**, followed by **Open** and any authentication macOS requests. It includes the German equivalents. The approval option follows a blocked launch and is time-limited; an absent option calls for another launch attempt before returning to Settings. Managed-device policy can prohibit an exception. The flow requires no Apple Developer membership or purchased certificate and introduces no quarantine-removal script, trust helper or global security-setting change. The guide does not establish publisher trust or make approval automatic. [Apple's instructions](https://support.apple.com/en-hk/102445) own the operating-system behavior.

The adjacent `forge.config.spec.ts`, included by the existing desktop test runner, evaluates the prepared real maker configuration and checks that the packaged app, destination link and readable guide remain in the visible layout. Native acceptance additionally makes the DMG, verifies it with `hdiutil verify`, mounts it read-only, checks all three entries and the Applications link, and inspects the Finder layout. A quarantined downloaded copy must then be installed and opened through the documented app-specific approval on a Mac; successful packaging alone does not prove Gatekeeper approval.

## Repository identity and migration boundary

The workflow and helper contracts bind to immutable repository ID `1440122208`. Renaming that repository and subsequently transferring it to Pixel Brewery preserve its ID; the former repository and forks do not satisfy this guard. A history-free migration retains the approved application source snapshot, including the complete owner-selected design-branch changes, in one parentless initial `main` commit. Source content is integrated without importing the former Git ancestry. Before removing the original repository, verify that every pull request and secondary branch is either represented in the approved snapshot or deliberately deferred under the owner's decision. At cutover, verify the new repository's ID, private visibility, parentless initial `main`, absence of imported tags, Releases, pull requests and pull refs, and inability to resolve former commits within it. Existing clones, independent copies, and platform retention are outside this repository-history boundary; this is not a claim of global erasure.

Uncommitted local modularization work remains preserved locally, outside the published initial snapshot. Keep its working files and recovery basis intact; port that work deliberately onto the new `main` after the cutover and verify it against that baseline. A history reset must not silently discard it or treat it as already integrated. Old Dependabot patches are not copied or merged blindly: Dependabot generates fresh updates against the new baseline, and each proposed update must pass the current checks. The explicit TypeScript exclusion and deliberate maintenance of the Pixel Brewery dependency family remain in effect.

GitHub can retain frozen head/base snapshots for closed pull requests after a history rewrite, preventing their reopening even when live branches have been restored. Finalize the new source root before asking Dependabot to generate replacements. The public baseline uses distinct `angular-updates`, `nx-updates`, `linting-updates`, `testing-updates`, `node-types`, and `github-actions-updates` group identities; group names identify Dependabot proposals as well as their branches. Keep the existing dependency patterns and ignore policies, and verify that replacement proposals originate from Dependabot against the final root. New group names do not clear separately stored ignore conditions. Do not rewrite `main` again after generating these proposals, or copy their dependency patches into `main` to bypass the normal five-check gate.

The repository does not inherit the former repository's Git tags, GitHub Releases, pull-request history, workflow runs, Pages configuration, or credential/settings evidence. Do not copy old refs or release assets back into it. The initial source snapshot retained package version `0.1.16` and a concise changelog baseline without old commit, pull-request, or compare links. Without stable tags, the first-release path uses that committed version and prepares its first patch as `0.1.17`, with tag `v0.1.17`. The fresh history requires neither a version reset nor recreation of `v0.1.16`. This preserved history boundary is separate from the evidence for each later publication.

## Public release configuration and acceptance

The repository is public as `pixel-brewery/symphony`, with immutable ID `1440122208` and default branch `main`. Publication validates that exact identity, name and visibility; later changes that violate the contract stop the release. GitHub API and Git writes resolve the current repository name from Actions, while the compiled default update origin is `https://pixel-brewery.github.io/symphony`. The bundle identifier `com.ruederennes.symphony` remains the established application identity for upgrades.

Pages publication requires an owner to configure the Actions build mode and admit `main` in the `github-pages` environment before the first run, with its HTTPS URL matching the compiled origin. Updating those site settings requires repository administration authority; the workflow's native token only validates them and deploys. No administration secret is added. The source contains the site generator and workflows; installers, immutable manifests and icons remain attached to GitHub Releases. Each site build recreates the full `releases/` and `channels/` tree plus the download page in staging, then deploys one Pages artifact. Actions artifact retention is not the history store. Stable is the Release explicitly marked `Latest`, while Canary is the highest fully published numeric version. A new successful release moves both channels; selecting an existing version for Stable changes that marker and republishes the site without rebuilding installers. Release publication verifies staged assets by their draft Release ID, then verifies canonical public download URLs after publication.

The [publication-branch migration contract](README.md#migration-from-the-publication-branch) preserves every existing version-manifest and icon byte in a Release-attached `symphony-pages-history.json` archive, including previously public metadata for draft Releases without publishing their installers. The first rebuild also validates the old channel choices and imports Stable's previous selection unless a release or promotion caller supplies its explicit intended version. The old `gh-pages` branch is deleted only after the Actions deployment passes byte-for-byte checks for every generated public URL; an explicit Git deletion lease atomically requires its revision to match the archived source. This contract and the local source do not by themselves establish that the remote migration has completed. The [CI/CD contract](README.md#cicd-configuration) defines the storage locations, permissions, complete reconstruction, failure handling and deployment evidence.

The main-only contribution contract requires human PRs and five successful job contexts: the complete Ubuntu/macOS/Windows source-quality matrix, then the macOS Electron E2E and package-smoke jobs. The native jobs both depend on the entire source matrix, whose `fail-fast: false` setting retains every platform's result. A final `Quality Gate` always runs and accepts only `success` from all three job owners, so failure, cancellation and skipped native acceptance cannot turn into a passing aggregate. Pull requests and merge-queue groups run the same complete verification. The live PR/check ruleset retains the [five exact context names](README.md#main-protection-and-release-app-prerequisites) and now additionally requires `Quality Gate` from GitHub Actions App `15368`. Activation followed direct proof of the passed aggregate in [run 41290003337](https://github.com/pixel-brewery/symphony/actions/runs/41290003337) and an independent ruleset read-back; workflow YAML alone does not update a ruleset. Required approving reviews remain zero for sole maintainer `RueDeRennes`, and PR creation remains limited to collaborators. The PR/check exception remains exclusive to release App `5547670`; the separate deletion/non-fast-forward rule retains no bypass. Do not add general administrator, human or all-Actions bypasses. Pages deployment grants no additional source-branch bypass.
