# Deployment and packaging

**Dokumentstatus:** Implementierter Ist-Stand

This page describes the implemented packaging and release preparation, followed by the outstanding live handover prerequisites. The complete update and publication contract is owned by [Desktop updates](README.md).

Nx builds Angular into `dist/apps/renderer/browser`, Electron Main and sandbox-compatible CommonJS preload into `dist/apps/desktop`, and the ESM Utility Process into `dist/apps/orchestrator`. Main resolves both renderer and child relative to its packaged module. Forge packages the repository with ASAR enabled and active platform makers for DMG, Debian, and Squirrel; the ZIP maker remains commented out for a later support expansion. The release pipeline selects ARM64 on every platform and publishes only the DMG, EXE, and DEB installer outputs. Forge accepts CI-provided macOS signing/notarization and Windows signing configuration without storing credential values in the repository.

The canonical Symphony mark and every generated application-icon format live under the top-level `resources/icons` directory. `yarn icons:generate` derives browser PNGs, menu-bar templates, and the native ICNS and ICO containers from that mark. Renderer and mobile builds copy their icons from the same directory, Electron Main uses its packaged resource copy for the window and macOS Dock icon, and Forge uses the native files for macOS, Windows, Debian, and installer metadata. Windows publication places the ICO beside each version manifest on the update origin so Squirrel can resolve the Control Panel icon without depending on the source repository.

Every macOS launch explicitly sets the Dock image from the active application's resources, including packaged builds. This prevents a same-name local rebuild from relying on an older icon retained by the operating system. Replacing a bundle on disk does not update the image already held by a running process; the new process applies the current image at startup. This image refresh keeps the established bundle identity and does not clear global operating-system caches.

The menu-bar templates use a 24-point canvas with 48-pixel Retina representations. The posthorn uses its full geometry without an additional inset; running and failed badges occupy the free space above its right arm. All three states preserve the same posthorn size and alignment, and badges do not obscure the mark. Native visual acceptance checks the rendered menu-bar size and the packaged Dock image as well as the generated files.

`yarn start` builds and launches the platform's packaged Symphony application so operating-system surfaces use the branded bundle name and icon. `yarn start:unpackaged` and `yarn dev` retain Electron's raw development bundle for diagnostics and live development; macOS identifies that upstream bundle as Electron in the Dock.

`yarn package:smoke` performs a production build, runs `electron-forge package`, then verifies the unpacked application contains the expected executable bundle and renderer assets. After the public handover, the desktop release workflow prepares one semantic Nx Release version for every successful `main` source commit. Verification, all native builds, and publication use the same metadata-only commit, transferred through an internal Git bundle. The workflow applies macOS Developer ID signing/notarization and Windows signing only when each capability's complete credential group is available, and uses a complete ad-hoc macOS bundle signature when Apple credentials are absent. Developer ID builds retain Hardened Runtime; the ad-hoc branch disables it because no stable Team ID exists for library validation of the embedded Electron Framework. The workflow verifies the ARM64 macOS bundle signature, rejects an incompatible ad-hoc runtime flag, verifies its DMG, and whitelists exactly one ARM64 installer per platform before upload. After the final source-revision check, it atomically pushes the version commit, changelog, and tag, then publishes and verifies the GitHub Release and channel manifests. The Debian package remains unsigned and requires no signing credential. Native automatic-update feeds remain unchanged while their commented ZIP and NuGet payloads are disabled; installer-only releases are detected in-app and replaced manually. The complete publication layout, optional GitHub Actions configuration, runtime lifecycle, and recovery policy are defined in [Desktop updates](README.md).

## Repository identity and migration boundary

The workflow and helper contracts bind to immutable repository ID `1440122208`. Renaming that repository and subsequently transferring it to Pixel Brewery preserve its ID; the former repository and forks do not satisfy this guard. A history-free migration retains the approved application source snapshot, including the complete owner-selected design-branch changes, in one parentless initial `main` commit. Source content is integrated without importing the former Git ancestry. Before removing the original repository, verify that every pull request and secondary branch is either represented in the approved snapshot or deliberately deferred under the owner's decision. At cutover, verify the new repository's ID, private visibility, parentless initial `main`, absence of imported tags, Releases, pull requests and pull refs, and inability to resolve former commits within it. Existing clones, independent copies, and platform retention are outside this repository-history boundary; this is not a claim of global erasure.

Uncommitted local modularization work remains preserved locally, outside the published initial snapshot. Keep its working files and recovery basis intact; port that work deliberately onto the new `main` after the cutover and verify it against that baseline. A history reset must not silently discard it or treat it as already integrated. Old Dependabot patches are not copied or merged blindly: Dependabot generates fresh updates against the new baseline, and each proposed update must pass the current checks. The explicit TypeScript exclusion and deliberate maintenance of the Pixel Brewery dependency family remain in effect.

The new repository does not inherit the former repository's Git tags, GitHub Releases, pull-request history, workflow runs, Pages configuration, or credential/settings evidence. Do not copy old refs or release assets back into it. The source snapshot keeps package version `0.1.16` and a concise changelog baseline without old commit, pull-request, or compare links. With no stable version tags, the release workflow's existing first-release path uses that committed version and prepares the next patch as `0.1.17`, with new tag `v0.1.17`. The fresh history does not require a version reset or recreation of `v0.1.16`. These migration rules specify the source and history boundary; they do not attest that a GitHub operation or publication has completed.

## Public activation prerequisites

Source migration, ownership transfer, and public visibility are separate operations. Publication requires the exact public name `pixel-brewery/symphony` and default branch `main`; it cannot publish an installer pointing at the Pixel Brewery feed while the repository is private or still belongs to `RueDeRennes`. GitHub API and Git writes resolve the current repository name from Actions, while the compiled default update origin is `https://pixel-brewery.github.io/symphony`. The bundle identifier `com.ruederennes.symphony` remains the established application identity for upgrades.

Before launch, the owners must verify the repository migration, complete the transfer and public-visibility decision, and deliberately enable Actions with usable capacity. Prepare `gh-pages` as a separate parentless root containing only `.nojekyll` and a neutral `index.html`, without importing former release metadata. This bootstrap may exist privately; it is not an update feed or a release. After transfer and public activation, configure Pages to serve that branch at `/` using the legacy branch-based build mode, with its HTTPS URL matching the compiled origin. Pages on GitHub Free requires a public repository. The [update-site bootstrap contract](README.md#cicd-configuration) defines the release prerequisite and the later manifest publication.

The intended main-only policy requires human PRs and all three repository checks, with zero required approving reviews for sole maintainer `RueDeRennes`. PR creation is already limited to collaborators; that setting does not establish main protection. Private organization repositories on GitHub Free cannot enforce the intended branch rules before public activation. After the owner's separate public-visibility decision, enable and read back the PR/check rule and a separate deletion/non-fast-forward rule. Only the PR/check rule grants an exception to the dedicated release App; the force/deletion rule has no bypass. Do not add general administrator, human or all-Actions bypasses, or apply these main rules to `gh-pages`.

The one-time release setup requires a private GitHub App with only repository Contents write authority, installed for exactly `pixel-brewery/synapse` and `pixel-brewery/symphony`, and repository variable `RELEASE_APP_ID`. Put `RELEASE_APP_PRIVATE_KEY` only in the `release-main` environment as an environment secret. Its custom deployment policy must allow exactly type `branch`, name `main`, with no required reviewers or wait timer. The environments and exact branch policy are already configured in both repositories, without App credentials. A live proof that the gate blocks other branches on private Symphony's current plan is still outstanding; successful configuration alone is insufficient. Verify that no same-named repository/organization secret exists because YAML cannot prove the resolved secret's origin. Configure the App's specific identity in the PR/check rule before relying on automated metadata pushes. The publication job uses that environment and creates a short-lived token for this repository only after all release checks; only the atomic `main`/tag push receives it. Registry access, GitHub Release APIs, Pages and workflow dispatch retain the native `GITHUB_TOKEN`. The [release authority contract](README.md#main-protection-and-release-app-prerequisites) defines the full ordering and credentials boundary. Prepared YAML does not create the App, install credentials or activate protection, and the private key must not be distributed to local release runners.

Recheck token permissions and optional platform-signing configuration on the repository; former-repository observations do not establish those prerequisites. Keep the confirmed personal code owner `@RueDeRennes` when applying review policy. All currently pinned Pixel Brewery dependencies are public registry packages; the actual short-lived Actions-token install still needs a successful live run, and no missing package ACL has been established. Prepared source and hosting configuration alone prove neither a public release nor a reachable installer feed. Validate one full live release, its public installer manifests, and native installation before relying on unattended delivery. Once configured, the dependency-merge and continuous-publication path remains unattended.

Install the first Pixel Brewery build manually on machines that still use the previous owner's compiled feed origin. That one-time replacement points later background checks at the public Pixel Brewery feed; a repository transfer alone cannot update an already installed application's origin.
