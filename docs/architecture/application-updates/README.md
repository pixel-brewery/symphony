# Desktop updates

**Dokumentstatus:** Implementierter Ist-Stand

## Implemented source and release evidence

The implemented capability joins release preparation, artifact verification, the public download page and channel publication, and Main-owned update checks. The supported product flow displays an available update, downloads and verifies its installer inside Electron Main on request, and launches that verified installer when the person chooses `Restart to update`. GitHub Releases owns the durable distribution data; GitHub Actions reconstructs and deploys the website and update paths to Pages. Each desktop publication is established by its own successful workflow, verified installer assets and public channel manifests; source changes or configured infrastructure are not evidence of a completed deployment or native installation test.

Publication evidence is separate from the source-history migration and hosting setup. [Packaging and public handover](packaging.md) records the preserved migration boundary, configuration and per-release acceptance requirements. The [Pages migration contract](#migration-from-the-publication-branch) distinguishes source implementation from the live switch and deletion of the former publication branch. A verified Synapse package release does not prove Symphony's desktop publication. Existing installations compiled with the previous owner's feed require the one-time replacement described below. The [functional update guide](../../project/application-updates/README.md) owns the user-facing workflow.

Symphony treats desktop updates as an operating-system lifecycle capability. Electron Main owns the fixed update origin, channel selection, checks, the in-app installer download and its verification, installer launch, native installation, and restart coordination. The sandboxed renderer receives only validated update state and named `get`, `check`, `download`, `channel.set`, and `install` requests through `window.desktop`. Feed and artifact URLs, credentials, arbitrary channels, filesystem primitives, and Electron objects never cross preload.

## Release channels and immutable artifacts

Every source change on `main` that affects code, configuration or operational instructions requests a semantic patch release. A lightweight classifier compares the complete push range before candidate preparation or dependency installation. An explicitly documentation-only push skips version resolution, verification, native builds and publication; it creates no release commit, tag, installer or channel update. Missing or unavailable history takes the full release path. Explicit `workflow_dispatch` requests always take that full path, even when the latest source change is documentation-only. The shared [repository-quality contract](../repository-quality/README.md) defines the allowlist and event comparisons.

The root `package.json` is an explicit private Nx application project, and Nx Release resolves the next version from the latest `v<version>` tag, falling back to the checked-in version for the first release. The configure job prepares and formats the version, lockfile, and root `CHANGELOG.md` once. It requires exactly one generated commit whose parent is the triggering source revision and whose changes are limited to those metadata files. An internal Git bundle carries that exact commit and tag to verification, all three ARM64 builders, and publication. The publisher verifies the same commit ID, source parent, and metadata-only changes again; it never runs a second version calculation. Only after verification and every native build succeed does it atomically push the version commit and tag, then create a draft GitHub Release with exactly one DMG, one EXE, one DEB, the generated changelog, and the version's `manifest.json` and `symphony.ico` metadata assets. It resolves that draft's numeric Release ID and uses the authenticated ID endpoint to verify the uploaded installer matrix. This staging check permits only the canonical repository's matching draft asset URL form because GitHub gives unpublished assets temporary `untagged-…` URLs and does not expose them through the public tag endpoint. The publisher then publishes that exact Release ID, explicitly selects it as `Latest`, and verifies the public tag and canonical advertised URLs again. An incomplete upload therefore does not become a public channel candidate, and a staging check never substitutes for public URL verification. GitHub adds its source ZIP and source `tar.gz` links automatically. A run refuses to reuse a remote tag or release, so published bytes remain immutable.

Release verification first runs `yarn node .agents/skills/symphony-docs/scripts/validate-docs.mjs docs`, then `yarn verify` on Ubuntu, macOS, and Windows. Its macOS gate also installs the mobile journey's Chromium dependency, runs the complete Electron E2E suite, and runs the existing `yarn forge:package` smoke check. The three native builders can start once preparation has bundled the exact candidate. Publication waits for the complete verification matrix and every installer. If stable version tags are absent, preparation adds Nx's `--first-release` flag while retaining the selected relative increment and the committed disk baseline. The fresh repository therefore starts its first patch release from the retained `0.1.16` package version and prepares `0.1.17` with tag `v0.1.17`; it does not republish `v0.1.16` or reset to a hardcoded initial version. Old tags and GitHub Releases are not prerequisites and must not be imported to seed the new history. The first-release flag changes version/changelog preparation, not repository history or remote refs; publication retains the normal verification and atomic metadata-push gates.

The normal push trigger selects `patch` for changes outside the documentation-only allowlist. `workflow_dispatch` accepts `patch`, `minor`, or `major` when an operator intentionally needs a different increment; the repository commands `yarn release:patch`, `yarn release:minor`, and `yarn release:major` dispatch those choices against `main`, while `yarn release:dry-run` previews a patch locally. Dispatch also accepts an optional `source_sha`: when supplied, the configure job requires it to equal that run's `GITHUB_SHA` before version preparation. These commands use the same publication owner for the durable version commit, tag, GitHub Release, and desktop assets. Release commits include the Actions skip marker because their prepared tree already passed the complete gate.

Each native release build opens the resulting ASAR to verify its package version and compiled update origin against the release inputs before uploading its installer. The macOS build also launches the packaged executable with an isolated profile. That acceptance test exercises the scheduled startup check against the canonical feed URL, makes a newer version visible, downloads and verifies the installer, and checks the file passed to the operating system before Symphony exits. The test supplies fixture responses at the HTTP boundary and intercepts the operating-system opener. Live Pages verification and native installation remain separate evidence.

The macOS pull-request gate and release workflow build the DMG from the already packaged application. If Forge reports that the Symphony volume disappeared during detach, they retry creation from that same package up to twice and preserve the output of every attempt. Any other error or exhausted retry budget fails the build. Both workflows verify the resulting disk image, and the pull-request gate exercises the packaged update journey before merge.

### Dependency merge to release request

A verified Dependabot merge uses the native `GITHUB_TOKEN`, which does not start another push-triggered workflow. The merge job therefore records `merged` and the exact `merge_sha` as job outputs. Its separate `request-release` job runs only for `merged == 'true'`, receives the retained merge SHA, and requests the ordinary patch release with `source_sha` set to that SHA. The request job has native-token `actions: write` and `contents: read`; the merge job retains its existing bounded merge permissions. Neither receives the release App key. Both check out trusted default-branch helpers rather than pull-request code, dependencies or artifacts. Requests serialize by merge SHA without cancelling an earlier request.

`tools/requestMergedRelease.mjs` requires the canonical public, non-fork repository ID/name, `main`, a complete source SHA and the active canonical release workflow. It checks current `main`, inspects canonical push/dispatch runs for that exact source and workflow, and rechecks `main` immediately before dispatch. The configure job's `source_sha` comparison closes the remaining gap if `main` moves between that final read and workflow creation. These workflow/helper changes are implemented in this checkout; their live activation requires publishing them to the default branch.

| Result              | Meaning and recovery                                                                                                                                                                                                                                                                           |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `requested`         | GitHub accepted the patch dispatch for the retained merge SHA. This is a release request, not evidence that verification or publication completed.                                                                                                                                             |
| `already-requested` | An existing canonical release run for that SHA is observable. No second candidate is requested. This result also covers failed or cancelled attempts; recover the original release run separately.                                                                                             |
| `superseded`        | `main` no longer equals the retained merge SHA. Nothing is dispatched for that older source. The newer source needs its own release evidence.                                                                                                                                                  |
| Request failure     | Invalid metadata, unavailable credentials or a failed API request fails this job with a controlled diagnostic. Inspect existing release runs, then retry only the failed `request-release` job; its successful merge dependency and outputs remain available, so no second merge is attempted. |

Retrying the merge job itself is not the recovery path for a dispatch failure after an already completed merge. If dispatch was accepted before its response was lost, the next request recognizes the existing run once it is visible. A failed or cancelled release attempt remains an operation on that original run and candidate; an `already-requested` result does not establish release success.

Publication is ordered so channel metadata can never outrun its artifacts. The release and its installer and metadata assets are created first, and every installer the version manifest advertises is then confirmed with the publishing job's short-lived repository token. The verifier rejects extra assets except the exact supported metadata names. Continuous publication explicitly marks the new release as GitHub's `Latest`, advancing both Stable and Canary. The manual Stable selection workflow verifies already published bytes and changes only the explicit `Latest` selection; Canary continues to use the highest fully published numeric version. The selected artifacts are never rebuilt. The download-site publisher reconstructs the complete metadata tree, generates each channel's `installer.json`, uploads a Pages artifact and deploys it with the official Pages actions. Publication and Stable selection serialize their changes and require the public files to match the prepared output before reporting success. Native Squirrel feeds remain absent while the archive payloads described below are disabled.

The supported release surface is ARM64-only: `Symphony-darwin-arm64-<version>.dmg`, `SymphonySetup.exe`, and `symphony_<version>_arm64.deb`. Forge's ZIP maker, the x64 matrix entries, and publication rules for ZIP and full NuGet payloads remain commented rather than deleted so the wider platform matrix can be restored deliberately. Electron's native macOS updater requires an application ZIP and Squirrel.Windows requires a full NuGet package, so these installer-only releases are installed by launching the downloaded, size- and SHA-256-verified platform installer and do not advance native Squirrel feeds. The immutable per-version `manifest.json` and the selected channel's small `installer.json` are served from `https://pixel-brewery.github.io/symphony` by default, or the matching GitHub Pages HTTPS custom domain named by the `SYMPHONY_UPDATE_BASE_URL` repository variable, while the three binaries are served from the canonical repository's GitHub Release. Both manifests record the platform, ARM64 architecture, size, SHA-256, and URL of every selected installer.

Every release follows a fixed distribution policy without platform certificates or Apple notarization. Forge seals every macOS app with the ad-hoc identity `-`, disables identity validation and Hardened Runtime, and fails if sealing fails. The seal has no stable Team ID; disabling Hardened Runtime allows the embedded Electron Framework to load. Every macOS release unconditionally verifies the strict deep bundle signature, requires the ad-hoc identity without the runtime flag, and verifies the DMG before upload. Windows and Debian installers are intentionally unsigned. There are no certificate imports, notarization submissions or certificate-backed verification branches. Review the [public source](https://github.com/pixel-brewery/symphony) and published SHA-256 values; download and run at your own discretion under the [MIT license](../../../LICENSE), as-is and without warranty. Operating-system trust prompts remain part of installation.

The macOS DMG exposes a bilingual first-launch guide above its application and Applications destination. It explains the per-app **Open Anyway** approval after an initial blocked launch; no Apple Developer membership, paid certificate, automatic trust change or quarantine-removal script is involved. The packaging owner retains the existing ad-hoc seal and integrity gates. [Disk-image composition and native acceptance](packaging.md#macos-disk-image-installation-and-first-launch) define the guide asset, public maker API, layout and distinction between a valid package and a successfully approved downloaded installation.

## Runtime lifecycle

The update coordinator remains isolated in Electron Main. Every check reads and validates the platform's installer manifest before consulting the legacy native updater. A newer installer produces `available` state and retains the installer's credential-free HTTPS URL, file name, declared byte count, and SHA-256 digest only inside Main. A manifest at the running or an older version produces `idle` directly, so a stale native Squirrel feed cannot falsely decide that a newer installer-only release does not exist. Origins that predate installer manifests retain the native updater fallback. Development builds, builds without a configured origin, and Linux builds expose an explicit disabled reason. Linux releases remain owned by the operating-system package manager because Electron does not provide a built-in Linux updater. Main checks 15 seconds after launch (10 seconds on a Squirrel first run), then hourly, after system resume and screen unlock, and one second after a channel change.

The Main-owned update coordinator has an exhaustive state union: `disabled`, `idle`, `checking`, `available`, `downloading`, `ready`, and `failed`. `downloading` optionally carries `targetVersion` and a `progress` share between 0 and 1; an in-app installer download always sets both, while the native updater's download carries neither and is rendered as indeterminate. `failed` carries `CHECK_FAILED`, `DOWNLOAD_FAILED`, or `INSTALL_FAILED` with a fixed product message. The coordinator never forwards raw updater errors, download URLs, file paths, or digests because those can contain distribution details. The main window's status bar, the menu-bar panel, and Settings share `DesktopUpdateStore`; the status bar shows `Symphony v<currentVersion>`, the icon-only download action while `available`, the same action disabled with a Mosaik `ProgressRing` replacing the icon in its content slot while `downloading`, and the labelled `Restart to update` action while `ready`. Settings remains the detailed surface for the current version, selected channel, latest state, manual check, and failure message. The functional workflow is described in [Symphony aktualisieren](../../project/application-updates/README.md); the status-bar contract is part of [window chrome and navigation](../window-and-navigation/README.md#statusleiste-version-und-update).

Main requests the canonical installer manifest without a query string, accepts JSON, and asks caches to revalidate the response. Pages verification compares each canonical channel response with the prepared manifest bytes using the same cache mode and media type. A stale response is retried within the publication verifier's bounded attempt budget. Other static Pages files still receive a per-attempt query parameter.

### In-app installer download

`updates.download` is accepted only while the coordinator is `available` with a retained installer. Main then starts the download asynchronously and answers `{ outcome: 'started' }`; a repeated request during the same download also answers `started` without a second transfer. Only when no in-app download can start does Main fall back to the previous handoff: it opens the retained installer URL in the operating-system browser and answers `opened`, or answers `not-available`. With the current coordinator both branches require the same `available` state, so the fallback is a defensive path. The renderer shows no toast for `started` and leaves progress to the status bar; for `opened` it shows `Update download opened.`.

The download contract, independent of Electron:

1. Re-validate the retained URL: `https:` only, without user, password, query, or fragment. Re-validate the file name against `^[A-Za-z0-9][A-Za-z0-9 ._+-]*$`, a single path segment whose suffix the manifest check already bound to the platform (`.dmg` on macOS, `.exe` on Windows) and to the last URL path segment.
2. Create the Symphony-owned download root `<operating-system temp directory>/symphony-updates` with mode `0700` if necessary and remove every earlier entry below it.
3. Create a fresh directory `<version>-<random>` below the root and open `<directory>/<file name>` exclusively (`wx`) with mode `0600`.
4. Fetch the installer with redirects followed. Reject a non-success status, a missing body, a final response URL that is no longer `https:`, and an uncompressed `Content-Length` that differs from the manifest's byte count before writing.
5. Stream the body into the file while hashing it with SHA-256. Abort as soon as more bytes arrive than declared. Abort when no chunk arrives for 60 seconds. Report the received byte count after each written chunk.
6. After the stream ends, require exactly the declared byte count and the declared lower-case hexadecimal SHA-256 digest, close the file, and return its absolute path.
7. On any failure or cancellation, close the file and remove the whole fresh directory, so no partial or unverified installer survives.

The coordinator converts received bytes into whole percent of the declared size and publishes a new `downloading` state only when the percent increases and at least 150 ms have passed since the previous publication, which bounds the IPC traffic to all renderer windows. Success records the verified path in Main memory and publishes `ready` with `targetVersion` and `downloadedAt`. Failure publishes `failed` with `DOWNLOAD_FAILED`; the next automatic or manual check reads the manifest again, publishes `available`, and a new download can start. Disposing the coordinator during application shutdown aborts a running download without publishing a failure; the adapter removes the partial file. The verified path is not persisted: after a restart, a ready in-app download is not reused and the next check offers the update again. A channel change, which is refused while `checking` or `downloading`, discards both the available installer and a downloaded one. Main suppresses its native "update ready" prompt for a download the person started through `updates.download`, because that person already watches the status-bar action turn into `Restart to update`.

### Installation

Before installation, Main asks the Utility Process for active operations. With no work, it installs immediately. When only executions are active, the native warning offers **Pause tasks and update**, which pauses them durably for automatic resumption after the restart, or **Later**. When an Issue Creator draft, local verification, managed local CI run, or developer-tool installation is also active, none of which can resume, the warning offers **Cancel tasks and update** or **Later**. **Later** returns `deferred`. If the Utility Process cannot prove a safe handoff, Main shows **Update restart is not safe yet**, returns `deferred`, and the downloaded update remains ready. Main then sets the confirmed-quit state and stops the restart and update timers, so the existing shutdown supervisor cannot restart the Utility Process during replacement.

For an in-app download, the coordinator opens the verified installer with the operating system (macOS mounts the disk image, Windows runs the setup program) and then quits Symphony so the installer can replace it. The opener accepts only a file whose directory lies below the Symphony download root. If the installer cannot be opened, Symphony stays running, clears the confirmed-quit state, reschedules checks, publishes `failed` with `INSTALL_FAILED`, and answers `not-ready`. For a native (Squirrel) download, the coordinator calls Electron's `quitAndInstall` exactly as before; the native path, its feeds, and its ready prompt **Symphony update ready** with **Restart and update** or **Later** are unchanged.

## CI/CD configuration

The compiled update origin defaults to `https://pixel-brewery.github.io/symphony`. API and Git writes use `github.repository`, while the workflow and helper guards bind to immutable repository ID `1440122208`, the public `pixel-brewery/symphony` repository. Renaming or transferring it preserves its ID; the former repository and forks do not satisfy the guard. Continuous publication and manual Stable selection also require that exact public repository name and default branch `main`. A later visibility or name change that violates this contract stops publication. Identity is checked before Pages metadata is requested. Pages uses the GitHub Actions publishing mode (`build_type: workflow`), with its served HTTPS URL matching the compiled origin. The publication path has no dependency on a `gh-pages` branch.

The source branch contains the generator, page template and workflows. Generated `index.html`, `channels/` and `releases/` directories exist only in a run's staging output and the deployed Pages site. They are not committed to `main` or another publication branch. A Pages artifact is a deployment transport, not the durable source for the next build: Actions artifact expiry must not remove historical update data or make a fresh deployment depend on an older workflow run.

Before publication, and again immediately before the atomic version/tag push, the release workflow verifies that `main` still points at the source revision it built. If a newer change arrived, the older run stops and the queued run owns the next release. Pages publication is explicitly requested by the release and Stable-selection owners; it does not rely on a token-created Release or branch push triggering another workflow implicitly. A separate site rebuild can deploy the already published distribution without creating a new application version. Pages configuration, public visibility, and an Actions policy that permits the official upload and deployment actions are owner prerequisites.

### Durable metadata and complete site reconstruction

The distribution has three separate storage responsibilities:

| Owner                        | Durable or generated content                                                                                                    |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| Application source on `main` | Site generator, page template, branded resource and publishing workflows.                                                       |
| GitHub Releases              | Installer binaries and each version's immutable `manifest.json` and `symphony.ico`; the migration archive for earlier metadata. |
| GitHub Pages                 | Generated download page, channel pointers, and the preserved versioned metadata paths.                                          |

A new release attaches its original version manifest and icon beside its three installers. The manifest has `schemaVersion: 1`, the numeric `major.minor.patch` version, original `sourceCommit`, original `createdAt`, and `files`. Each file supplies `platform`, `architecture`, `name`, `bytes`, a lowercase SHA-256 `sha256`, and its canonical credential-free GitHub Release download `url`. The manifest remains the integrity record for the installer bytes. Reconstructing a site must not recalculate its timestamp, source revision, file sizes or digests.

Metadata predating the switch is retained in the `symphony-pages-history.json` asset attached to the public `Latest` Release selected when migration runs. Its version-1 shape is `{ "schemaVersion": 1, "files": [{ "path": "releases/<version>/manifest.json", "data": "<base64 bytes>" }] }`; icon entries use `releases/<version>/shared/symphony.ico`. It contains only those two supported path forms. The capture includes every version present on the former publication branch; the inspected starting tree contains versions `0.1.17` through `0.1.27`. The earlier versions that are currently draft Releases retain their already public metadata paths without publishing their installers or adding them to the download catalogue. While the old branch remains during a retry, an existing archive may be extended only if every previously archived path retains exactly the same bytes. After successful branch cleanup, the retained archive is a read-only reconstruction input and is not regenerated with every release or copied into source control. Its owning public Release must remain available.

The collector enumerates published numeric Releases and loads their version metadata and any history archive. It verifies uploaded asset state, byte counts, SHA-256 digests and canonical repository URLs, rejects incompatible manifests and unsafe archive paths, and fails on conflicting bytes for the same historical path. A missing or invalid metadata source fails collection rather than silently dropping a previously published version. Draft Releases are excluded from the download catalogue and channel candidates; archive entries remain available for compatibility regardless of whether their original Release is still public.

Stable is the published numeric Release returned by GitHub's explicit `Latest` selection. Canary is the highest fully published numeric version. Both selected Releases must expose a complete verified installer matrix. Continuous publication sets `Latest` explicitly for its new version; manual Stable selection changes it explicitly after verifying the chosen published version. This preserves the existing rule that a new successful release advances both channels while a later manual selection can move Stable independently. A caller may pass `stable-version` as the expected already verified selection; the site job requires the collected `Latest` version to match it rather than treating the input as permission to select an unverified version. The workflows own that marker; after migration, an unrelated manual change to GitHub's `Latest` selection changes the input of the next rebuild.

The builder copies every preserved `releases/<version>/manifest.json` and `releases/<version>/shared/symphony.ico` without rewriting their bytes. For each selected channel it projects the manifest's installer entries into `/channels/<stable|canary>/<platform>/arm64/installer.json`, with `schemaVersion: 1`, `version`, `platform`, `architecture` and an `artifact` containing the original `name`, `bytes`, `sha256` and `url`. These are the same public paths and schema consumed by already installed applications. The builder generates the root download page from the verified Stable catalogue entry and includes a separate Canary area only when its version differs. Metadata is escaped before rendering, and page links use the validated installer and release-note URLs.

The complete generated tree is uploaded and deployed as one Pages artifact. The reusable `Publish Symphony Downloads` workflow accepts an explicit call, manual dispatch, and changes to its site source on `main`. Continuous release and Stable selection call it after their successful Release operation; it does not depend on a token-created Release implicitly triggering an event. The single main-only job uses concurrency group `desktop-update-publication` without cancelling an active run. Its native job token receives `contents: write` for one-time archive preservation, explicit channel selection and conditional branch deletion, `pages: write` for deployment, and `id-token: write` for the deployment identity. Website generation does not need the release App private key or a registry installation. A failed collection, generation or deployment leaves the prior deployed site available. A failed verification after deployment requires an explicit retry or redeployment; a workflow conclusion alone must not be presented as a successful public-file check.

The Pages publishing mode and environment admission are owner-managed prerequisites. An owner with repository administration authority switches the existing site to `build_type: workflow` while preserving its HTTPS origin and configures the `github-pages` environment to admit branch `main`. The job cannot repair its own missing environment admission because GitHub evaluates that policy before running its steps. The [Pages configuration update API](https://docs.github.com/en/rest/pages/pages#update-information-about-a-github-pages-site) requires both Pages write and Administration write authority; the native `GITHUB_TOKEN` cannot gain Administration permission. The ordinary workflow therefore validates the configured mode and origin instead of changing site settings. No long-lived administration token or new administration secret is introduced. Subsequent deployments need only the documented native job permissions.

Manual GitHub Release publication and edits are handled by `Refresh Downloads After Release Changes`. Its `published` and `edited` event job validates the canonical public repository and uses only `actions: write` to dispatch `publish-pages.yml` with the fixed `--ref main`. It performs no checkout and ignores Release-provided source refs and payload data. The trusted main workflow then reloads and validates the current durable metadata; the event itself is not proof of a complete release. Missing or incompatible metadata stops publication while retaining the deployed site. This dispatcher covers owner-initiated Release changes; native-token release creation still needs the explicit reusable call because `GITHUB_TOKEN` events do not start the event workflow. Repeated requests use the same serialized, complete reconstruction path and do not rebuild installers.

### Migration from the publication branch

This is a migration contract, not evidence that the remote switch has already completed. The former `gh-pages` branch stored the complete public metadata tree and a static bootstrap `index.html`; release publication never refreshed that placeholder. Removing the branch is the final migration step, after the following acceptance sequence:

1. An owner performs the Pages-mode and `github-pages` environment prerequisite changes above, then runs trusted `main` publication. Record the former branch revision and capture its version-manifest, icon and channel files. Coordinate with publication so no new version or channel change is lost while that source is captured.
2. Create the history archive from those exact bytes and attach it to the public `Latest` Release selected for migration. If an asset of that name already exists, require the new archive to preserve every existing path and its bytes before replacement; only additional historical paths are allowed. Conflicting or removed content stops migration. Download the uploaded archive again and require full byte equality with the prepared archive. Do not publish draft Releases, change installer bytes or rewrite source history.
3. Without an explicit `stable-version`, validate that the captured Stable feeds select one version across all three operating systems, verify that published version, and import it into GitHub's explicit `Latest` marker before collection. The resulting complete channel tree must then match the captured tree byte for byte. A reusable release or promotion caller instead supplies its intended already verified Stable version, which must match the collected `Latest` marker. Promotion must still reproduce the old Canary tree exactly. Only a call with both an explicit Stable selection and `advance-canary: true` may replace that legacy Canary selection; the boolean defaults to `false`, and continuous release passes `true` for its newly verified version. This prevents migration from resetting an earlier manual Stable choice or silently advancing Canary during promotion. Incompatible captured state stops migration rather than being silently replaced.
4. Build the complete site from the Release metadata alone. Verify that the archived manifest and icon bytes are reproduced, both selected channels point at their intended complete Releases, and the download page links to the corresponding public installers. Deploy the generated artifact to the preconfigured Actions site with pinned official upload/deployment actions and verify every generated public URL byte for byte against the staged output. This includes the download page, site resources, every preserved versioned path and current channel manifests.
5. Delete `refs/heads/gh-pages` only after that acceptance succeeds and its captured data is still current. The cleanup first checks the live revision, then uses a Git deletion with an explicit `--force-with-lease` binding to the archived revision. A branch change between the read and deletion therefore rejects the deletion instead of removing unarchived data. The completed source and future publication path must not read or recreate it.

Before the deletion gate, any failed migration check preserves the branch and its recovery basis. After deletion, a clean checkout reconstructs the site from the Release assets and channel selection; neither an old Actions artifact nor the removed branch is required. Restore a failed Pages deployment by rebuilding those retained inputs or redeploying a previously verified complete artifact. Do not compensate for a deployment failure by inventing a new application version, overwriting immutable metadata or recreating an ongoing publication branch. A changed Pages origin remains a separate compatibility change for installed applications.

Optional repository-level GitHub Actions variables:

- `SYMPHONY_UPDATE_BASE_URL` replaces the default Pixel Brewery origin with the HTTPS URL actually served by this repository's GitHub Pages configuration, including a configured custom domain. It must contain no credentials, query, or fragment. Nx includes the value in the desktop build cache key because Electron Main compiles it into the package. Existing installations continue to request their compiled origin.

For the ownership handover, installations compiled with the previous owner's origin need a one-time installation of the first Pixel Brewery release. GitHub redirects repository links after a transfer but [does not redirect the associated Pages site](https://docs.github.com/en/repositories/creating-and-managing-repositories/transferring-a-repository). Publishing a new feed cannot change an origin compiled into an older application. Once that first installer is installed, normal background checks use the Pixel Brewery origin and offer subsequent releases through the existing Download action.

Platform certificate and notarization configuration is not supported. Forge does not consume legacy Apple or Windows signing environment variables, so ambient values cannot select certificate signing. macOS always receives the same ad-hoc seal, and Windows and Debian remain unsigned. The GitHub `RELEASE_APP_*` configuration below authenticates repository publication only; it does not provide operating-system publisher trust.

Dependency installation and Nx's local version preparation receive only the short-lived `GITHUB_TOKEN` with `packages: read`. ## Verification and recovery

Unit tests cover installer-manifest validation, version comparison, trusted-origin enforcement, state transitions, disabled environments, and install readiness. `HttpInstallerUpdateAdapter.spec.ts` additionally covers file names that could leave the download directory, streaming into a private file with progress and removal of earlier downloads, rejection of a mismatching `Content-Length` before writing, removal of a cancelled partial download, and opening only installers below the download root. `UpdateCoordinator.spec.ts` covers whole-percent progress at most every 150 ms, a failed download followed by a new offer, opening the installer and quitting instead of the native updater, staying open when the installer cannot be opened, no in-app download without an installer while the native download stays indeterminate, and cancellation on dispose without a failure. `tools/prepare-update-publication.spec.ts` covers both publication layouts, the exact three-installer ARM64 matrix, channel installer pointers, ignored ZIP/NuGet/x64 maker output, origin validation, and flat asset-name collisions. The published-assets verifier rejects missing or changed installers and unknown extra assets while accepting the documented metadata names. Site acceptance covers durable-history restoration without a publication branch, independent Stable selection, Canary ordering, incomplete-release rejection, unsafe metadata paths and links, escaped page content, byte-preserved historical metadata, and existing installer-feed schemas. The release-workflow policy specs evaluate the real Forge and prepared Squirrel configuration with synthetic legacy certificate variables on each platform, require fixed ad-hoc macOS sealing and unsigned installers, and reject reintroduced certificate inputs or operations. They preserve public repository guards, immutable official action references, dependency-token scope, complete native build gates, and one source-bound metadata commit. They also require unconditional strict macOS bundle and DMG verification with launch-compatible ad-hoc runtime flags. Electron E2E verifies the sandboxed API and the status-bar sequence: no update action without an update, the icon-only `Download Symphony <version>` action while `available`, a progress ring reporting `aria-valuenow` while `downloading`, and `Restart to update` while `ready`. Release acceptance must additionally install the three native ARM64 installers, exercise the fixed ad-hoc macOS manual-install path and Windows trust prompts, restart, retain configuration and workspace state, and resume a paused durable execution.

Git ref publication, Release asset upload, `Latest` selection and Pages deployment are separate durable operations; only the version commit and tag share one atomic push. If an asset operation fails after that push, inspect the failed run and finish publication for the same verified version and bytes. The workflow deliberately refuses to overwrite the existing tag, assets, or version manifest; rerunning an already completed metadata push is not an automatic recovery mechanism. If the Release and its metadata are complete but Pages fails, rebuild the download site from those retained inputs without rebuilding installers or advancing the application version. A changed `Latest` marker can exist before its matching Pages deployment succeeds, so recover by publishing the current verified selection rather than assuming the failed run rolled it back. Do not move channel pointers to an incomplete release. A successful source or policy test does not replace live public-file checks and native-installer acceptance.

Update rollback is forward-only: channel publication can be stopped immediately, but clients that already installed a bad version need a newly versioned build containing the revert; an ad-hoc-signed macOS installation requires manual replacement. Persistence and settings migrations must therefore be transactional, retain a pre-migration recovery checkpoint, and declare their minimum compatible application version before any release introduces a schema change.
