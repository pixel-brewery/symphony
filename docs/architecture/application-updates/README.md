# Desktop updates

**Dokumentstatus:** Implementierter Ist-Stand

## Implemented source and release evidence

The implemented capability joins release preparation, artifact verification, channel publication, and Main-owned update checks. The supported product flow displays an available update, downloads and verifies its installer inside Electron Main on request, and launches that verified installer when the person chooses `Restart to update`. The public repository has configured main protection, release App credentials and a built Pages site. Each desktop publication is established by its own successful workflow, verified installer assets and public channel manifests; configured infrastructure is not a completed desktop release or native installation test.

Publication evidence is separate from the source-history migration and hosting setup. [Packaging and public handover](packaging.md) records the preserved migration boundary, live configuration and per-release acceptance requirements. A built bootstrap page advertises no application version, and a verified Synapse package release does not prove Symphony's desktop publication. Existing installations compiled with the previous owner's feed require the one-time replacement described below. The [functional update guide](../../project/application-updates/README.md) owns the user-facing workflow.

Symphony treats desktop updates as an operating-system lifecycle capability. Electron Main owns the fixed update origin, channel selection, checks, the in-app installer download and its verification, installer launch, native installation, and restart coordination. The sandboxed renderer receives only validated update state and named `get`, `check`, `download`, `channel.set`, and `install` requests through `window.desktop`. Feed and artifact URLs, credentials, arbitrary channels, filesystem primitives, and Electron objects never cross preload.

## Release channels and immutable artifacts

Every source commit on `main` requests a semantic patch release. The root `package.json` is an explicit private Nx application project, and Nx Release resolves the next version from the latest `v<version>` tag, falling back to the checked-in version for the first release. The configure job prepares and formats the version, lockfile, and root `CHANGELOG.md` once. It requires exactly one generated commit whose parent is the triggering source revision and whose changes are limited to those metadata files. An internal Git bundle carries that exact commit and tag to verification, all three ARM64 builders, and publication. The publisher verifies the same commit ID, source parent, and metadata-only changes again; it never runs a second version calculation. Only after verification and every native build succeed does it atomically push the version commit and tag, then create the GitHub Release with exactly one DMG, one EXE, one DEB, and the generated changelog. GitHub adds its source ZIP and source `tar.gz` links automatically. A run refuses to reuse a remote tag or release, so published bytes remain immutable.

Release verification first runs `yarn node .agents/skills/symphony-docs/scripts/validate-docs.mjs docs`, then `yarn verify` on Ubuntu, macOS, and Windows. Its macOS gate also installs the mobile journey's Chromium dependency, runs the complete Electron E2E suite, and runs the existing `yarn forge:package` smoke check before any native release build or publication can proceed. If stable version tags are absent, preparation adds Nx's `--first-release` flag while retaining the selected relative increment and the committed disk baseline. The fresh repository therefore starts its first patch release from the retained `0.1.16` package version and prepares `0.1.17` with tag `v0.1.17`; it does not republish `v0.1.16` or reset to a hardcoded initial version. Old tags and GitHub Releases are not prerequisites and must not be imported to seed the new history. The first-release flag changes version/changelog preparation, not repository history or remote refs; publication retains the normal verification and atomic metadata-push gates.

The normal push trigger selects `patch` to preserve continuous delivery for every source change. `workflow_dispatch` accepts `patch`, `minor`, or `major` when an operator intentionally needs a different increment; the repository commands `yarn release:patch`, `yarn release:minor`, and `yarn release:major` dispatch those choices against `main`, while `yarn release:dry-run` previews a patch locally. These commands never create a parallel release path: CI remains the sole owner of the durable version commit, tag, GitHub Release, and desktop assets. Release commits include the Actions skip marker because their prepared tree already passed the complete gate. A Dependabot merge performed with `GITHUB_TOKEN` does not generate another push-triggered workflow, so the merge wrapper explicitly dispatches `release.yml` after a verified merge. After the release's atomic version push, publication explicitly dispatches `rebase-dependabot.yml` to refresh remaining bot branches, including when a later asset or feed operation fails.

Publication is ordered so channel metadata can never outrun its artifacts. The release and its three installer assets are created first, and every URL the version manifest advertises is then confirmed with the publishing job's short-lived repository token. The verifier also rejects any configured GitHub Release asset that is absent from the manifest. Each platform and architecture then receives an `installer.json` pointer under Stable and Canary. Native Squirrel pointers remain unchanged while the archive payloads described below are disabled. The manual Stable selection workflow verifies already published bytes and moves only Stable's installer pointers without rebuilding the selected artifacts. Both workflows serialize their origin writes, request a Pages build explicitly, require the expected metadata commit to finish building, and compare the public installer feed bytes with the prepared files before reporting success.

The supported release surface is ARM64-only: `Symphony-darwin-arm64-<version>.dmg`, `SymphonySetup.exe`, and `symphony_<version>_arm64.deb`. Forge's ZIP maker, the x64 matrix entries, and publication rules for ZIP and full NuGet payloads remain commented rather than deleted so the wider platform matrix can be restored deliberately. Electron's native macOS updater requires an application ZIP and Squirrel.Windows requires a full NuGet package, so these installer-only releases are installed by launching the downloaded, size- and SHA-256-verified platform installer and do not advance native Squirrel feeds. The immutable per-version `manifest.json` and the selected channel's small `installer.json` are served from `https://pixel-brewery.github.io/symphony` by default, or the matching GitHub Pages HTTPS custom domain named by the `SYMPHONY_UPDATE_BASE_URL` repository variable, while the three binaries are served from the canonical repository's GitHub Release. Both manifests record the platform, ARM64 architecture, size, SHA-256, and URL of every selected installer.

Platform signing is never a release gate. A complete macOS signing group enables Developer ID signing with Hardened Runtime, and a complete notarization group additionally enables Apple notarization; configured signatures are verified before upload. Missing or partial groups are ignored with a workflow warning, so Forge instead seals the complete app bundle with an ad-hoc identity that needs no Apple account. Because an ad-hoc identity has no stable Team ID, that branch disables Hardened Runtime so macOS library validation does not reject the embedded Electron Framework during process launch. Every macOS build must pass strict deep signature and DMG verification before upload, and the workflow additionally rejects an ad-hoc main executable that still carries the runtime flag. Ad-hoc signing provides bundle integrity but no Apple trust, Hardened Runtime, or notarization, so Gatekeeper still requires an explicit operator override. Windows Authenticode signing is likewise optional, although unsigned installers lose SmartScreen reputation. The Debian artifact has no package-signing step or credential requirement and is distributed unsigned with a SHA-256 value in the immutable version manifest.

## Runtime lifecycle

The update coordinator remains isolated in Electron Main. Every check reads and validates the platform's installer manifest before consulting the legacy native updater. A newer installer produces `available` state and retains the installer's credential-free HTTPS URL, file name, declared byte count, and SHA-256 digest only inside Main. A manifest at the running or an older version produces `idle` directly, so a stale native Squirrel feed cannot falsely decide that a newer installer-only release does not exist. Origins that predate installer manifests retain the native updater fallback. Development builds, builds without a configured origin, and Linux builds expose an explicit disabled reason. Linux releases remain owned by the operating-system package manager because Electron does not provide a built-in Linux updater. Main checks 15 seconds after launch (10 seconds on a Squirrel first run), then hourly, after system resume and screen unlock, and one second after a channel change.

The Main-owned update coordinator has an exhaustive state union: `disabled`, `idle`, `checking`, `available`, `downloading`, `ready`, and `failed`. `downloading` optionally carries `targetVersion` and a `progress` share between 0 and 1; an in-app installer download always sets both, while the native updater's download carries neither and is rendered as indeterminate. `failed` carries `CHECK_FAILED`, `DOWNLOAD_FAILED`, or `INSTALL_FAILED` with a fixed product message. The coordinator never forwards raw updater errors, download URLs, file paths, or digests because those can contain distribution details. The main window's status bar, the menu-bar panel, and Settings share `DesktopUpdateStore`; the status bar shows `Symphony v<currentVersion>`, the icon-only download action while `available`, the same action disabled with a determinate Mosaik `ProgressRing` while `downloading`, and the labelled `Restart to update` action while `ready`. Settings remains the detailed surface for the current version, selected channel, latest state, manual check, and failure message. The functional workflow is described in [Symphony aktualisieren](../../project/application-updates/README.md); the status-bar contract is part of [window chrome and navigation](../window-and-navigation/README.md#statusleiste-version-und-update).

### In-app installer download

`updates.download` is accepted only while the coordinator is `available` with a retained installer. Main then starts the download asynchronously and answers `{ outcome: 'started' }`; a repeated request during the same download also answers `started` without a second transfer. Only when no in-app download can start does Main fall back to the previous handoff: it opens the retained installer URL in the operating-system browser and answers `opened`, or answers `not-available`. With the current coordinator both branches require the same `available` state, so the fallback is a defensive path. The renderer shows no toast for `started` and leaves progress to the status bar; for `opened` it shows `Update download opened.`.

The download contract, independent of Electron:

1. Re-validate the retained URL: `https:` only, without user, password, query, or fragment. Re-validate the file name against `^[A-Za-z0-9][A-Za-z0-9 ._+-]*$`, a single path segment whose suffix the manifest check already bound to the platform (`.dmg` on macOS, `.exe` on Windows) and to the last URL path segment.
2. Create the Symphony-owned download root `<operating-system temp directory>/symphony-updates` with mode `0700` if necessary and remove every earlier entry below it.
3. Create a fresh directory `<version>-<random>` below the root and open `<directory>/<file name>` exclusively (`wx`) with mode `0600`.
4. Fetch the installer with redirects followed. Reject a non-success status, a missing body, a final response URL that is no longer `https:`, and an uncompressed `Content-Length` that differs from the manifest's byte count before writing.
5. Stream the body into the file while hashing it with SHA-256. Abort as soon as more bytes arrive than declared. Abort when no chunk arrives for 60 seconds. Report the received byte count after each written chunk.
6. After the stream ends, require exactly the declared byte count and the declared lower-case hexadecimal SHA-256 digest, close the file, and return its absolute path.
7. On any failure or cancellation, close the file and remove the whole fresh directory, so no partial or unverified installer survives.

The coordinator converts received bytes into whole percent of the declared size and publishes a new `downloading` state only when the percent increases and at least 150 ms have passed since the previous publication, which bounds the IPC traffic to all renderer windows. Success records the verified path in Main memory and publishes `ready` with `targetVersion` and `downloadedAt`. Failure publishes `failed` with `DOWNLOAD_FAILED`; the next automatic or manual check reads the manifest again, publishes `available`, and a new download can start. Disposing the coordinator during application shutdown aborts a running download without publishing a failure; the adapter removes the partial file. The verified path is not persisted: after a restart, a ready in-app download is not reused and the next check offers the update again. A channel change, which is refused while `checking` or `downloading`, discards both the available installer and a downloaded one. Main suppresses its native "update ready" prompt for a download the person started through `updates.download`, because that person already watches the status-bar action turn into `Restart to update`.

### Installation

Before installation, Main asks the Utility Process for active operations. With no work, it installs immediately. When only executions are active, the native warning offers **Pause tasks and update**, which pauses them durably for automatic resumption after the restart, or **Later**. When an Issue Creator draft, local verification, managed local CI run, or developer-tool installation is also active, none of which can resume, the warning offers **Cancel tasks and update** or **Later**. **Later** returns `deferred`. If the Utility Process cannot prove a safe handoff, Main shows **Update restart is not safe yet**, returns `deferred`, and the downloaded update remains ready. Main then sets the confirmed-quit state and stops the restart and update timers, so the existing shutdown supervisor cannot restart the Utility Process during replacement.

For an in-app download, the coordinator opens the verified installer with the operating system (macOS mounts the disk image, Windows runs the setup program) and then quits Symphony so the installer can replace it. The opener accepts only a file whose directory lies below the Symphony download root. If the installer cannot be opened, Symphony stays running, clears the confirmed-quit state, reschedules checks, publishes `failed` with `INSTALL_FAILED`, and answers `not-ready`. For a native (Squirrel) download, the coordinator calls Electron's `quitAndInstall` exactly as before; the native path, its feeds, and its ready prompt **Symphony update ready** with **Restart and update** or **Later** are unchanged.

## CI/CD configuration

The compiled update origin defaults to `https://pixel-brewery.github.io/symphony`. API and Git writes use `github.repository`, while the workflow and helper guards bind to immutable repository ID `1440122208`, the public `pixel-brewery/symphony` repository. Renaming or transferring it preserves its ID; the former repository and forks do not satisfy the guard. Continuous publication and manual Stable selection also require that exact public repository name and default branch `main`. A later visibility or name change that violates this contract stops publication. The configure job checks live identity before requesting Pages metadata, then requires Pages to be configured from `gh-pages` at `/`, with its served URL matching the compiled origin, before building a release.

The update-site bootstrap is owner-managed rather than a release-workflow side effect. Its `gh-pages` branch has an independent parentless root, separate from both the former repository history and the application source root. The initial tree contains only `.nojekyll` and a neutral `index.html`, without old version directories, channel pointers, installer manifests or release assets. Pages is configured and has built that site using `build_type: legacy`, branch `gh-pages`, path `/`, at the HTTPS origin expected by the application. A successful bootstrap build proves hosting, not an available application version. The release workflow requires the branch and matching live Pages configuration to remain in place; it does not create them. Only verified publication writes immutable version manifests and channel installer pointers.

Channel metadata accumulates on `gh-pages` so one channel can move without disturbing the other or earlier version manifests. Before publication, and again immediately before the atomic version/tag push, the workflow verifies that `main` still points at the source revision it built. If a newer change arrived, the older run stops and the queued run owns the next release. `GITHUB_TOKEN` pushes do not start a Pages build, so each origin writer calls the documented Pages build API explicitly and waits for the expected origin commit. It does not attempt to create or change Pages settings. Creating a site requires repository administration authority that the release token does not have. Pages configuration, public visibility, and an Actions policy that permits these workflows are owner prerequisites.

Optional repository-level GitHub Actions variables:

- `SYMPHONY_UPDATE_BASE_URL`: replaces the default Pixel Brewery origin with the HTTPS URL actually served by this repository's GitHub Pages configuration, including a configured custom domain. It must contain no credentials, query, or fragment. It is compiled into Electron Main, so changing it only affects builds produced after the change; existing installations keep the origin they were built with. This workflow does not deploy to an unrelated external hosting service.

For the ownership handover, installations compiled with the previous owner's origin need a one-time installation of the first Pixel Brewery release. GitHub redirects repository links after a transfer but [does not redirect the associated Pages site](https://docs.github.com/en/repositories/creating-and-managing-repositories/transferring-a-repository). Publishing a new feed cannot change an origin compiled into an older application. Once that first installer is installed, normal background checks use the Pixel Brewery origin and offer subsequent releases through the existing Download action.

Repository secrets can optionally provide signing material. macOS signing uses `APPLE_SIGNING_IDENTITY`, `MACOS_CERTIFICATE_BASE64`, and `MACOS_CERTIFICATE_PASSWORD` as one all-or-none group. Apple notarization uses `APPLE_API_KEY_BASE64`, `APPLE_API_KEY_ID`, and `APPLE_API_ISSUER` as a second all-or-none group and is enabled only when signing is also enabled. Windows signing uses `WINDOWS_CERTIFICATE_BASE64` and `WINDOWS_CERTIFICATE_PASSWORD` as an all-or-none group. A missing or partial macOS group selects ad-hoc signing; a missing or partial Windows group selects an unsigned build. Partial groups are ignored and annotated rather than passed to Forge. Linux has no signing secrets. None of these values are embedded in the application or persisted by Symphony.

Dependency installation and Nx's local version preparation receive only the short-lived `GITHUB_TOKEN` with `packages: read`. All current Pixel Brewery dependencies are public registry packages; each job must still authenticate its own exact dependency downloads. No package PAT is required or passed to PR CI. Read jobs cannot write the repository, all checkouts disable persisted Git credentials, and platform signing material is configured only after dependency installation and build. The publication job installs no dependencies. Its native workflow token has `contents: write` for GitHub Release APIs and the `gh-pages` channel commit, `actions: write` for the explicit Dependabot refresh dispatch, and `pages: write` for the requested feed build. Only the final atomic `main` and version-tag push uses the separate release App token. API and Git credentials are passed only to the steps that use them. Approved default-branch workflow code and official action code remain trusted within each job's permissions.

## Main protection and release App prerequisites

Pull-request creation is restricted to collaborators, and human source changes to `main` require a PR. The `Repository Quality` contract requires five exact successful job contexts for the current PR revision:

- `Agents, Format, Lint, Typecheck, Test and Build (ubuntu-latest)`
- `Agents, Format, Lint, Typecheck, Test and Build (macos-latest)`
- `Agents, Format, Lint, Typecheck, Test and Build (windows-latest)`
- `Electron E2E`
- `Package smoke test`

The source-quality job expands to Ubuntu, macOS and Windows with `fail-fast: false`, so one failure does not cancel the other source-platform checks. Both native acceptance jobs retain their macOS host and declare `needs: quality`; they start only after the entire source matrix succeeds and may then run in parallel. The five required results therefore mean three source-platform jobs plus Electron E2E and package smoke, not five individual commands inside a job. The trusted Dependabot helper requires all five current successful results and rejects older Ubuntu-only three-job runs. Its canonical workflow, immutable repository, event, latest-attempt, tested-head and current-main gates remain in force.

The main PR/check rule must use that exact five-context set; read back its live configuration independently of the source change. Required approving reviews remain zero because `RueDeRennes` is the sole maintainer. Deletion and non-fast-forward prevention retain a separate main-only rule with no bypass actors. Only release App `5547670` bypasses the PR/check rule; no administrator, human-maintainer or general GitHub Actions exemption exists. These main-only rules do not cover other branches or tags, so the native workflow token can continue publishing to `gh-pages`.

Private release App `5547670` is installed only for the public `pixel-brewery/synapse` and `pixel-brewery/symphony` repositories. An installation-token check confirmed exactly those repositories, **Contents: read and write** and implicit **Metadata: read** permission. Both repositories have `RELEASE_APP_ID` configured and `RELEASE_APP_PRIVATE_KEY` stored only as an environment secret in `release-main`, with no same-named repository or organization secret. The environment's custom deployment policy allows exactly type `branch`, name `main`, with no required reviewers or wait timer. The native `GITHUB_TOKEN` is not the main bypass identity. Preserve and recheck these live scopes when rotating credentials or changing settings: YAML cannot distinguish the resolved key's secret origin, and an environment name alone configures no branch restriction.

The publication job selects `environment: release-main`, and only that job checks whether the App key is available. Missing resolved App settings or a failed token request stops publication. A repository/organization-secret fallback is forbidden by the operator contract; its absence is not a source-verifiable secret-provenance check. After the complete verification/build matrix, prepared-commit and asset-metadata checks, and final source-freshness check, the job requests a short-lived installation token for the current owner and this repository alone, limited to `contents: write`. Only the atomic fast-forward `main` and version-tag push receives that token. PR workflows, dependency installation, registry access, GitHub Release APIs, Pages operations and dispatches do not receive it. The separate force/deletion rule still applies to the App. Its PR/check bypass permits the already verified metadata commit; it does not remove the workflow's source, version, tag or concurrency checks.

Dependabot continues to merge through its verified PR using the trusted helper, without the release App. The generated release commit retains `[skip ci]`, so the explicit Dependabot refresh after publication remains necessary. Human PR merges request the normal release through their push event; native-token bot merges explicitly dispatch it. Real releases use CI or the existing `yarn release:patch`, `yarn release:minor` and `yarn release:major` dispatch commands. A direct human release push is incompatible with the active PR-only policy; local previews confer no bypass or publication authority.

Continuous dependency merges and publication remain approval-free and require no platform-signing credentials. The manual Stable selection workflow references an environment named `stable`; that name alone provides no protection. Its owner may configure branch restrictions and a required reviewer for that separate manual operation without adding an approval to continuous releases. The SHA-256 version manifest remains the artifact integrity record; this change does not enable attestations. The [successful Synapse package release](https://github.com/pixel-brewery/synapse/actions/runs/41130701417) exercised this App's protected-main push and package verification. Symphony still requires its own successful desktop publication for each candidate, followed by separate native-installer acceptance; shared App configuration and a built Pages site do not establish either result.

## Verification and recovery

Unit tests cover installer-manifest validation, version comparison, trusted-origin enforcement, state transitions, disabled environments, and install readiness. `HttpInstallerUpdateAdapter.spec.ts` additionally covers file names that could leave the download directory, streaming into a private file with progress and removal of earlier downloads, rejection of a mismatching `Content-Length` before writing, removal of a cancelled partial download, and opening only installers below the download root. `UpdateCoordinator.spec.ts` covers whole-percent progress at most every 150 ms, a failed download followed by a new offer, opening the installer and quitting instead of the native updater, staying open when the installer cannot be opened, no in-app download without an installer while the native download stays indeterminate, and cancellation on dispose without a failure. `tools/prepare-update-publication.spec.ts` covers both publication layouts, the exact three-installer ARM64 matrix, channel installer pointers, ignored ZIP/NuGet/x64 maker output, origin validation, and flat asset-name collisions. The published-assets verifier rejects missing, changed, or extra configured assets. The release-workflow policy spec preserves optional signing, public repository guards, immutable official action references, dependency-token scope, complete native build gates, and one source-bound metadata commit. It also requires a structurally valid macOS bundle, verified DMG, and launch-compatible ad-hoc runtime flags. Electron E2E verifies the sandboxed API and the status-bar sequence: no update action without an update, the icon-only `Download Symphony <version>` action while `available`, a progress ring reporting `aria-valuenow` while `downloading`, and `Restart to update` while `ready`. Release verification must additionally install the three native ARM64 installers, verify any configured platform signature, exercise the ad-hoc-signed macOS manual-install path where Apple signing is absent, restart, retain configuration and workspace state, and resume a paused durable execution.

Git ref publication, Release asset upload, and Pages deployment are separate durable operations; only the version commit and tag share one atomic push. If an asset or Pages operation fails after that push, inspect the failed run and finish publication for the same verified version and bytes. The workflow deliberately refuses to overwrite the existing tag, assets, or version manifest; rerunning an already completed metadata push is not an automatic recovery mechanism. Do not move channel pointers to an incomplete release. A successful source or policy test does not replace the first live token, signing, platform-installer, and Pages smoke checks.

Update rollback is forward-only: channel publication can be stopped immediately, but clients that already installed a bad version need a newly versioned build containing the revert; an ad-hoc-signed macOS installation requires manual replacement. Persistence and settings migrations must therefore be transactional, retain a pre-migration recovery checkpoint, and declare their minimum compatible application version before any release introduces a schema change.
