# Workspace model

“Workspace” has two distinct meanings:

- **Workspace Definition**: a strict customer/project ownership boundary for provider accounts, configuration, SQLite state, AI homes, repositories, CI, and executions.
- **Execution Workspace**: one Git worktree owned by one execution inside that Workspace Definition.

The active `WorkspaceViewScope` may select one or several Workspace Definitions. Aggregation changes only presentation and provider queries. It does not create cross-workspace Delivery Contexts, share credentials, or move execution data.

Within a Workspace Definition, the organization model is also isolated: positions describe responsibilities, agents fill positions, teams assign delivery phases, provider manifests declare capabilities, and route policies select only accounts owned by that workspace. A ticket is delegated to one responsible team member, while the executing agent can change by phase or failover. A provider failure selects the next healthy route candidate for the same agent and then hands the preserved worktree, implementation contract, changed-file snapshot, completed checks, and open steps to the team's explicit fallback agents in order. Candidate and provider health, observed latency, last-known success, usage, and circuit cooldown are persisted only in that workspace's SQLite state. A positively detected rate limit or exhausted quota additionally cools the workspace-owned AI account, so every route sharing that account is skipped while another workspace or account remains unaffected. Runtime admission is separately bounded by the route policy's `maxParallelExecutions`; its queue is keyed by workspace and route policy and therefore cannot consume another workspace's capacity. Account-scoped CLI model evidence is cached only by workspace, account, and explicit model; missing or failed evidence never broadens into another account and never becomes an assumed lockout. Provider continuation IDs survive only for the exact session-affine route candidate and are discarded across every other boundary. Neither mechanism may draw from another workspace.

Goals, execution records, events, route telemetry, account cooldowns, and worktree paths are persisted in that same workspace state. Workspace export/import carries organization, provider manifests, routes, and gateway metadata but removes credentials and machine paths. Deleting a workspace removes each of those owned configuration and persistence records. Global Settings shows only a workspace directory; opening one entry is the only way to inspect or change that organization's employees, teams, accounts, routes, and execution boundaries.

Delivery-group discovery is isolated by the same boundary: candidates must share workspace, Delivery Context, repository, and provider column. Every workspace receives Analyzer proposals and critical-path markers, but `automaticDeliveryGroupingEnabled` defaults to false and is the explicit opt-in for activating a fully gated `joint-delivery` proposal without a second operator confirmation. The setting travels with workspace export/import; it never authorizes cross-workspace or cross-repository grouping.

The production Git adapter resolves the repository from the work item's explicit repository binding. Ambiguous multi-repository work items are rejected before execution. Analyzer receives a detached worktree and a read-only agent sandbox. Solver/revision receives a new named `codex/work-<id>-<slug>` branch in an execution-owned worktree. Neither path permits mutation of the user's ordinary checkout, automatic commit, push, merge, or default-branch changes.

The Git provider's [worktree snapshot helper](../../libs/providers/git/src/lib/worktree-snapshot/createWorktreeSnapshot.ts), when invoked, archives the selected current file bytes through its existing filtered, NUL-delimited path list and content hash. It passes only the local basename `worktree-snapshot.tar.gz` as tar's output argument and runs tar from the output directory, while the source directory and list file remain explicit inputs. This prevents GNU tar from interpreting a Windows drive-qualified output path such as `C:` as a remote archive host. File selection, exclusions, modes and snapshot hashing are unchanged. This helper contract does not introduce an automatic snapshot flow or extend managed local CI beyond its existing macOS host requirement.

A Workspace Definition may own several enabled repository bindings. Adding and enabling a repository is the explicit authorization for manual and automatic AI work to use that source identity; work items select one binding and ambiguous multi-repository items are rejected before execution. A repository does not require an ordinary user checkout. **Prepare locally** creates or refreshes an application-owned clone below the Workspace Definition and persists that machine-local path without executing project code. Local verification remains a separate flow with its own structured capability approval. See [Local repository verification](local-repository-verification.md).

Path validation permits only direct `execution-*` children of configured per-workspace execution roots, rejects traversal and symlinks, and removes Git worktrees through `git worktree remove --force`. Cleanup inventories every configured workspace root, skips queued/running/waiting executions, and reports removed, missing, skipped, and failed counts. Successful implementation workspaces remain until an explicit handoff or cleanup because their uncommitted change is the current artifact.
