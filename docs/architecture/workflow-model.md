# Workflow model

A Symphony workflow is provider-neutral orchestration policy. The tracker owns native work-item states; its adapter maps those states to `backlog`, `ready`, `executing`, `review`, `completed`, or `blocked`. Azure DevOps process states are mapped through the provider's state categories; GitHub Project states are mapped from the dynamically discovered Status options.

## Board columns and workflow states

Board columns are provider-owned and never synthesized. Every option of a GitHub Project's `Status` field becomes one `BoardColumn` (`id` = option id, `label` = option name, `sourceId` = the work-item source) in project order; an Azure DevOps source exposes the columns of its bound Kanban board (`team` + `boardId`) or, without a board, the work-item states of the loaded work-item types. Renaming a column in the provider only changes its label. Each work item carries `boardColumnId` (its provider column) next to the internal `state`, so the board groups by column while the orchestration policy reads the workflow state. The projection contains exactly the provider columns; the only presenter-side bucket is "No column" for items the provider reports without one.

The mapping column → workflow state is configuration only: `workItemSources[].columnMappings` (`columnId` → `workflowState`), edited in the board settings editor. Providers apply nothing but that mapping at runtime — an unmapped column stays visible, its items carry the `unmappedWorkflowState` (`blocked`, so autonomy and analysis pickup skip them while manual actions stay available), and a transition into a workflow state without a mapped column fails with a settings hint instead of guessing. `suggestWorkflowState` (label heuristic, plus Azure state categories and board column types) exists only to pre-fill the editor via `work-item-sources.columns`; the saved mappings are always explicit. Analyzer/Solver transitions target `ready` and `executing`, so the editor warns when either is unmapped.

One work-item source is one board. A workspace can hold several boards; `activeViewScope.workItemSourceId` selects the board shown on the board view (a missing selection merges every board in scope by workflow state, then by label). Board discovery (`github.projects.list`) lists projects owned by the signed-in account and projects linked to the workspace repositories.

Execution state is separate from work-item state. `queued`, `running`, `waiting`, `succeeded`, `failed`, and `cancelled` describe local Analyzer/Solver work and never become synthetic Azure DevOps columns. Analyzer and Solver transition work items only through `WorkTrackingPort`; the local execution database remains authoritative for agent progress.

GitHub Projects may additionally expose `Assistant phase` as the provider-neutral assistance-action role. Its options map only to `None`, `Create`, `Analyze`, and `Solve`. Those values express the shared action, while execution status stays local. Distributed ownership is a separate `WorkItemCoordinationPort`; the visible action cannot act as a lock because GitHub Project field updates have no compare-and-set precondition.

Create, Analyze/Re-analyze, Implement/Rework, and CI control are fixed Symphony actions. AI is explicit opt-in. `work-item-creation`, `analysis`, and `solution` skill roles select an instruction package but cannot redefine provider bindings, sandbox policy, persistence, or allowed external mutations.

Runtime-level automatic execution is a separate explicit opt-in. When enabled, durable [remote GitHub automation](remote-automation.md) maps authorized Issue/Project changes and named comment commands onto those same fixed actions. Work-item state and prior execution history decide whether a generic synchronization signal analyzes or implements; remote text cannot introduce a new command kind or bypass the execution policy.

[Autonomous execution](autonomous-execution.md) is a second, independent opt-in. Its Utility-Process cycle uses the same fixed actions to re-analyze failed work, analyze Backlog or explicit `Analyze` actions, implement the newest successful analysis in Ready, and report the verification outcome of delivered pull requests to the workflow supervisor, which alone moves them into the acceptance gate after its guards pass. One configurable per-installation capacity bounds every AI start regardless of its UI, mobile, remote-command, or autonomous origin; shared provider claims prevent the installations from spending those independent slots on the same ticket. Work items whose workflow record is parked (`retry-wait`, `blocked`, `human-required`, `quarantined`) are excluded from autonomous selection; scheduled retries and resolved blockers are resumed by the workflow maintenance pass on its own schedule, independent of this opt-in.

Work-item creation/editing uses provider-neutral title, body, type, revision, labels, assignees, repository bindings, and optional provider fields. Only the explicit Save/Create action mutates Azure DevOps. The AI creator produces a reviewable draft; it never writes directly to Azure DevOps, GitHub, or CI.
