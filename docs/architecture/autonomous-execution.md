# Autonomous execution

Symphony can operate the provider-neutral workflow without an open renderer. The operator explicitly enables **Run backlog analysis, ready implementations, failed retries, and pull-request status synchronization automatically** in Runtime settings. This authorization is independent from remote GitHub comment automation: either feature can be enabled without the other.

Autonomy schedules the inner execution phases; the durable goal remains the outer completion authority. Analyzer converts the delegated objective into a versioned implementation contract, Solver executes only that contract, deterministic worktree and repository checks gate review, and an explicit review decision either achieves the goal, requests another bounded revision, or blocks it. Provider and agent failover may continue the same phase, worktree, and contract, but neither a provider response nor a terminal execution state can mark the goal achieved. The deterministic checks are the repository-defined restore, build, lint, and unit-test steps of [Local repository verification](local-repository-verification.md); a managed worktree carries no installed dependencies, so restore belongs to them, while end-to-end steps stay outside the solve loop. A check that cannot run reports the missing toolchain and blocks the goal instead of discarding the completed implementation.

A red deterministic check does not end the run on its own. The implementation is already in the worktree and already passed its contract scope, so only its result is wrong, and the solve loop hands the failing output back to the same agent in the same worktree for a bounded number of repair rounds — **Verification repair attempts per run** in Runtime settings, two by default, zero to switch repair off. Each round is recorded on the run stream as a warning and appends its own verification report to the goal, so the evidence of what stayed red survives. The agent receives the failing step's output at repair length rather than the short tail an operator surface shows, because a build runner's summary footer fits in the short tail and the failing assertion above it does not. A contract-scope violation is never repaired: the run reached for paths its position forbids, and repeating the same contract would only repeat the reach.

Once the budget is spent the execution fails and keeps its worktree under **Retain failed execution workspaces**. The implementation step then offers _Repair implementation_ rather than _Retry implementation_: the next start continues that retained worktree and branch, records itself as a revision of the failed run, and carries the recorded failure into its request. Only when the worktree is gone does a start cut a new branch from the default branch, because only then is there nothing left to continue.

A work item carrying the `autonomy:excluded` label is excluded from autonomous analysis, implementation, and failed-work retry selection. Label matching ignores surrounding whitespace and letter case. The exclusion does not cancel an execution that already started, block a manual action, or reject an authorized remote GitHub command. Pull-request status synchronization continues so delivered work still reaches the acceptance gate: it reports the verification outcome to the workflow supervisor, which applies the guarded transition. Removing the label makes an otherwise eligible work item available to the next autonomous cycle. GitHub labels belong to their issue repository, so a Project spanning multiple repositories must define the label in every participating repository.

The orchestrator Utility Process owns one single-flight autonomous cycle. It runs immediately on activation and startup, then at the configured autonomous work interval (15 minutes by default). Each cycle synchronizes delivered pull requests before filling available execution capacity. The application-wide capacity defaults to three and is enforced again at the Analyzer/Solver entry point, so desktop, mobile, remote-command, recovery, and autonomous requests cannot bypass it. An operator-paused execution retains duplicate-work protection but does not consume capacity. A requested resume is filled before later capacity can remain unused; disabling autonomous work prevents new autonomous selections without stopping already-running executions. Each cycle drains the execution queue described in [Execution lifecycle](execution-lifecycle.md) before it selects anything itself, so a step an operator deliberately queued always takes the next free slot ahead of whatever the board offers; autonomy then spends only the capacity the queue leaves behind.

Several contributor-owned Symphony installations may serve the same GitHub Project concurrently. Each GitHub connection represents the contributor authenticated on that machine; one GitHub account is not shared across machines. GitHub assignees are descriptive issue metadata and never restrict which installation may analyze or implement a ticket; acquiring a claim does, however, record the acting account as the issue's only assignee, so the board always shows exactly who triggered the running action. Before any tracker transition or workspace preparation, every AI start must acquire the provider-neutral work-item claim described in [Execution lifecycle](execution-lifecycle.md). The provider creates that deterministic repository ref atomically, so accounts and machines compete through the same exclusivity mechanism. A losing installation defers the candidate and continues filling its capacity from other tickets.

The GitHub Project single-select field named `Assistant phase` is a shared action projection with exactly `None`, `Create`, `Analyze`, and `Solve`. It is not an execution-status field: local `running`, `waiting`, `succeeded`, `failed`, and `cancelled` records remain in SQLite. `Analyze` can request analysis even when the Project Status is already Ready, `Solve` is actionable only on the claim-owning machine that has the successful local analysis, and `Create` belongs to work-item creation rather than Analyzer/Solver scheduling. An absent or `None` value preserves state-based backlog and ready scheduling. Acquiring a claim writes `Analyze` or `Solve`; successful analysis advances it to `Solve`; successful implementation or explicit cancellation returns it to `None`.

Work is selected deterministically by oldest creation time and then stable work-item ID. Available slots are assigned in fair rounds across three lanes, so an existing failure or long Ready queue cannot starve Backlog reduction:

1. A latest failed Analyzer, Solver, or revision is moved to `ready` when necessary and re-analyzed. A later cycle implements the resulting analysis, so failed implementation is not repeated against an unchanged plan.
2. A `ready` item whose newest execution is a successful analysis starts a solution or revision.
3. A `backlog` item starts read-only analysis. Analyzer claims it into `ready` before preparing its detached analysis workspace.

The next round repeats those lanes in the same order when capacity exceeds three or a lane is empty. With the default capacity of three and work in every lane, one retry, one implementation, and one new Backlog analysis start together.

Cancelled work is never retried automatically. Active executions retain their slots across `queued`, `running`, and recoverable `waiting` states. A distributed-claim collision is deferred instead of creating a second execution, and so is an autonomous selection that loses the last slot - autonomy defers rather than queueing, because the queue holds operator decisions and a self-refilling autonomous queue would never drain.

When every eligible AI account is temporarily rate limited or out of quota, the execution remains durably `waiting`. A provider-declared retry/reset time delays reactivation directly instead of generating a rapid local retry loop; the wait remains cancellable and is re-evaluated after application restart. Restoring authentication or changing the account configuration clears its local cooldown so the next activation can probe immediately.

## Pull-request synchronization

An autonomous solution or revision is explicit authorization to deliver only its managed non-default implementation branch and create or reuse its pull request. It does not approve or merge. On every cycle, Symphony reads the status of persisted pull requests through the provider-neutral delivery port:

- an open or closed, unmerged pull request moves an `executing` work item to `review`;
- a merged pull request moves an `executing` or `review` work item to `completed`.

GitHub approval and merge remain manual GitHub actions. After those actions, no Symphony Board mutation is required. Provider responses and credentials remain inside the provider adapter; the application receives only `open`, `closed`, or `merged` plus the draft flag.

The autonomy setting is disabled by default. Existing installations receive the safe defaults of disabled, 15 minutes, and three parallel executions through settings-schema migration. Enabling it does not replay GitHub comments or change the separate authorization for remote commands.
