# FlowBoard adaptation

## Reference findings

The FLAMOX365 task and order views define flow views as projections over typed collections. Each projection supplies stable item keys, a column resolver, configured columns, title/subtitle functions, and a signal grouping items by column. Templates then render Mosaik `mosaik-flow-board`, `mosaik-flow-board-column`, and `mosaik-flow-board-column-item` wrappers with title, meta, subtitle, empty, and actions slots. Column counts and empty states are explicit. The bootstrap views disable drag-and-drop where persistence semantics are not available.

## Provider-neutral model

`OrchestrationBoard` owns an ordered list of `WorkflowColumn` values and `WorkItemCard` values. A column carries a stable workflow-stage ID, display label, ordinal, and external mapping reference. A card carries a work-item ID, display reference, execution summary, severity, blocked reason, and current internal workflow state.

GitHub project status names are never used as internal state enums. Configuration (`columnMappings` on the work-item source, with a label heuristic as default) maps a provider status option to a workflow-stage ID. The view renders the provider's own columns—labels and ordering come from the project—and uses the mapped workflow state only for orchestration; see [workflow-model.md](workflow-model.md#board-columns-and-workflow-states).

## Bootstrap behavior

- Columns and simulated items come from the same typed contract used by future tracker adapters.
- A card click opens the dedicated Mosaik task drawer used by the FLAMOX365 task board pattern; Board content never grows an inline details column.
- The drawer starts only its own work-item ID and keeps manual execution as the default. It projects the matching execution events as a live timeline, followed by the task result or actionable failure.
- Each board card projects the latest persisted execution for its work item. Running cards show an indeterminate progress bar plus the newest event; terminal cards show the completed or failed outcome.
- Each board card also shows the provider-neutral labels and assignee handles supplied by the tracker. GitHub-specific response shapes remain inside the GitHub adapter.
- Provider columns keep their original order and are the only columns; Symphony never synthesizes workflow-stage columns. Items the provider reports without a column land in a presenter-owned "No column" bucket that exists only while such items exist.
- The page header offers a board selector once the selected workspaces expose more than one board (work-item source). Selecting a board shows only its columns and items and makes it the target of new work items; "All boards" merges columns across boards by workflow state and label.
- Pushed execution events and local SQLite reconciliation update runtime state without reloading GitHub. The board reloads from GitHub only on initial startup, when the operator uses its refresh action, or at the configurable background interval. That interval is measured in minutes, defaults to 15 minutes, and cannot be configured below 15 minutes.
- Blocked and failed items use semantic variants plus visible text.
- FlowBoard runs in Mosaik's controlled mutation mode. Drag-and-drop emits intent first; Symphony writes the provider transition and only the next authoritative projection changes the Angular DOM. Failed writes therefore cannot leave a card in a column the provider rejected.
- Active, column-aligned `DeliveryGroup` values render as one `mosaik-flow-board-column-item-group`. The target ticket is always the root and front card. The column count still counts the underlying issues. A paused group with provider or revision drift renders its members separately in their real provider columns and gives each member the same align-or-dissolve action.
- The middle of an item or stack is a grouping target; its edges and the column surface remain move/reorder targets. Item-to-item, item-to-stack, stack-to-item, and stack-to-stack grouping all preserve the target root. Symphony interprets the generic Mosaik event only after enforcing workspace, Delivery Context, repository, revision, claim, pull-request, and size boundaries.
- Open Analyzer proposals with a shared change surface mark every affected card as `Take together?` or `Critical path`. Moving one of those cards into another lane opens the evidence drawer before any provider write, where the operator can group and move all members or keep them separate and move only the original card.
- Stable keys and signal-level grouping avoid repeated domain traversal during Angular change detection.
- Horizontal board scrolling preserves column width and is the deliberate small-window behavior.

## Delivery-group workflow

`IDeliveryGroupProposal` stores the evidence-backed `duplicate | joint-delivery | dependency | collision | unrelated` assessment without a numeric confidence. `IDeliveryGroup` retains root-first membership, source revisions, shared workflow stage, activation source, pull-request reference, and synchronization state. Automatic discovery shortlists only Analyzer-stage issues in the same workspace, source, repository, and provider column, and proposes every related set as one root-led cluster (bounded to five members) instead of competing pairs. It remains proposal-only by default; the workspace option `automaticDeliveryGroupingEnabled` activates only assessments that prove a shared change surface, compatible acceptance criteria and verification, current revisions, and no open decisions, claims, or pull requests.

Manual bundling has two entry points: dragging one item onto another (`manual-drag`) and multi-selecting cards (`manual-select`). Before either path proceeds, a mode dialog asks the operator to copy the tickets directly or analyze their relationship with AI first. Direct grouping is the default for an explicit operator decision: it activates the local visual group in one request, records the operator attestation, and deliberately skips Analyzer execution plus tracker relation labels and comments. The AI option retains the evidence proposal and confirmation workflow. Neither mode has an artificial desktop or provider time limit; cancellation remains an explicit workflow action rather than an elapsed-time cutoff.

Board multi-select uses the native Mosaik FlowBoard selection API: the board runs with `selection-mode='multiple'` permanently, every card renders the board-owned selection checkbox in its header (`selection`/`selectionCheckbox` parts) without activating the card on a checkbox click, and the selected state is the native theme border accent plus `aria-selected` on the card host — Symphony adds no duplicate selected badge. The presenter's selection is event-sourced from `flowBoardSelectionChanged` (`{ selectionMode, selectedItemKeys }`): an ordered mirror keeps still-selected keys in their stored order, appends newly selected keys, and drops deselected ones, preserving first-selected-is-root semantics the event itself does not guarantee. The card context menu's `Select for delivery` entry drives the same native path through the board's `handleItemSelect(item)` — the entry point the checkbox itself uses — because the item's bare `select()`/`deselect()` would neither update the board's selection bookkeeping nor emit the event. Clearing (the toolbar action and the auto-clear once an activated group covers the selection) goes through the board element's `clearSelection()`, bridged from the presenter's clear-request signal by the view (`viewChild` of the flow board); the presenter mirror empties eagerly because `clearSelection()` only re-announces a selection that was still non-empty. The toolbar's `Deliver together (N)` action uses the first-selected card as root; while a boundary rule blocks it, the disabled action names the violated rule in its tooltip. A manual selection is bounded to ten members instead of the automatic five and may span provider columns, while workspace, Delivery Context, and repository remain hard boundaries in every path.

AI-backed confirmation enforces two distinct gate classes. The safety gates — a member already carrying an active claim, a member already publishing a pull request, or open decisions left by the assessment — always block activation and cannot be bypassed. The evidence gates — a proved `joint-delivery` relation, a non-empty shared change surface, and compatible acceptance criteria and verification — may be bypassed only for a manually assembled proposal by an explicit operator attestation: the evidence drawer states that the Analyzer found weak evidence, its confirm action becomes `Deliver together anyway`, and the attestation (timestamp plus optional reason) is persisted for audit on the confirmed proposal and on a group the confirmation newly activates; a confirmation that extends an already active group records it on the proposal alone. Direct grouping has no Analyzer evidence gates, but it still enforces repository, workspace, Delivery Context, size, revision, and active-claim boundaries before activation. Automatic activation continues to require every gate, and member revisions must still match the assessment in every path — drift stales the proposal instead of activating it.

Confirming a proposal that overlaps one active group extends that group instead of creating a second one: the existing root, workflow stage, and branch identity are retained, new members are moved to the root column, and open proposals fully covered by the activated group become `stale`. A proposal spanning two different active groups is refused until one group is dissolved, and a group that already publishes a pull request cannot take new members mid-delivery.

An active group's root card shows its ticket count left-aligned in the Mosaik FlowBoard item's `eyebrow` slot. That slot belongs to the title group above `title`, so the badge remains above the headline and aligned beside the board-owned selection checkbox without Symphony overriding the component's internal layout.

The compact group projects its own context trigger through Mosaik's group-level `actions` slot, outside the deliberately non-interactive root card. Moving forward, backward, to a selected column, or by drag-and-drop always uses the same root transition followed by member alignment, so the group remains one board entry. The menu also exposes the shared process and pull-request actions, offers explicit re-alignment while a group is paused, and opens the existing details drawer before a destructive dissolve is confirmed.

The root remains the public `workItemId`, goal anchor, managed worktree owner, and branch-naming input. Analyzer and Solver receive every member snapshot and one root-led request. Claims are acquired in stable item-ID order and rolled back together after a partial failure. GitHub issues remain independent records and the shared pull request carries one closing reference per member.

## Later performance path

Mosaik FlowBoard owns its internal layout and drag controllers. If boards exceed the bootstrap scale, pagination is applied at tracker ingestion and per-column windowing is evaluated against Mosaik's own component behavior before adding virtualization. The domain model remains unchanged.
