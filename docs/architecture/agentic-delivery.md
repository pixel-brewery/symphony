# Agentic pull-request delivery

Agentic delivery extends the existing execution lifecycle; it is not a second CI bot. A global disabled-by-default policy and an independent repository CI-binding opt-in must both permit observation before Symphony evaluates a workflow failure. Existing failures are recorded as a baseline when a binding is first activated, so enabling the feature cannot retroactively spend tokens, rerun workflows, or modify branches.

The GitHub adapter lists operational runs independently of the renderer's selected view and reduces one failed run to provider-neutral jobs, steps, attempt, revision, and a bounded redacted failed-output excerpt. Logs are untrusted input. A deterministic classifier handles source, workflow, infrastructure, transient, authorization, and unknown failures before any agent starts. `ENOSPC`, runner loss, and similar infrastructure evidence never starts a source repair. Authorization failures always stop for operator action. A transient or infrastructure failure may request one idempotently journaled rerun only when its separate toggle permits it.

Source, workflow, and unknown failures may enter the existing Analyzer/Solver lifecycle when the corresponding controls permit them. `ci-diagnosis` is a read-only analysis-role execution. `ci-repair` is a revision-role execution with workspace-write access to the same retained managed non-default worktree and branch that produced the pull request. Both require the configured and locally prepared repository binding and use assigned portable skills, immutable skill snapshots, application-wide capacity, distributed work-item ownership, progress events, token accounting, pause/cancel semantics, and provider continuation recovery. Diagnosis never edits files. Repair never receives authority to merge or push a default branch.

```mermaid
stateDiagram-v2
    [*] --> observed
    observed --> classified
    classified --> stopped: operator-only or disabled policy
    classified --> awaiting-ci: allowed one-time rerun
    classified --> diagnosing: AI diagnosis allowed
    diagnosing --> repairing: diagnosis succeeded and class permits repair
    diagnosing --> failed: diagnosis failed
    repairing --> awaiting-ci: branch and pull request reconciled
    repairing --> failed: repair or delivery failed
    awaiting-ci --> resolved: later run succeeded
    awaiting-ci --> classified: later attempt failed
```

`AgenticDeliveryRecord` is the durable side-effect journal. It keys one provider run attempt, branch, revision, pull request, source execution, failure fingerprint, policy attempt, diagnosis execution, repair execution, rerun intent, state, and timestamps. Intent is saved before a rerun or delivery side effect. Commit/push recovery is idempotent: the delivery adapter commits only pending changes, pushes the same validated branch, reuses its open pull request, and creates a replacement only when that separate policy toggle allows it. A later successful workflow run resolves the journal record.

Application quit, Utility Process failure, sleep, network interruption, and provider-session loss reuse the normal durable execution recovery. The retained managed worktree and immutable skill snapshot allow the same diagnosis or repair to resume after settings or skill assignments change. A complete machine shutdown cannot execute remote work; on the next launch the Utility Process scans operational runs, reconciles journaled states and external pull-request state, and resumes without intentionally duplicating the recorded rerun, execution, branch, or pull request.

The policy independently controls observation, AI diagnosis, source repair, workflow repair, pull-request review-flow eligibility, managed branch updates, CI reruns, replacement pull requests, per-phase token guidance, daily token use, attempts, repair concurrency, and repeated-failure cooldown. Pull-request review is a registered portable-skill flow role; provider review-event ingestion remains subject to the same policy and must not bypass this lifecycle.

Managed branch updates also reconcile a Symphony-created pull request whose head is behind its base. The provider adapter projects only the provider-neutral base relationship (`current`, `behind`, `conflicting`, `unknown`) and exact observed head revision. When both the global policy and repository CI-binding opt-in permit it, the autonomous cycle asks GitHub to update that retained non-default branch with an expected-head precondition. GitHub owns every merge commit — the update-branch merge and the final merge alike; Symphony never rebases or force-pushes, never bypasses branch protection, and never merges the pull request. A concurrently moved head is benign: GitHub rejects the stale expected-head precondition and the next cycle simply re-inspects. The update itself is applied only to an open, non-draft pull request whose observed source branch still matches the retained managed workspace branch.

The loop is bounded and deduplicated. Candidates are the successful deliveries of the observed work items, ordered oldest delivery first, and at most twenty pull requests are inspected per cycle so a backlog cannot monopolize the single-flighted autonomous cycle with provider round trips. Each pull request is inspected at most once per tick even when several work items share it, and that single observation also serves pull-request synchronization later in the same cycle. One `unknown` mergeability observation is normal while GitHub computes it in the background; five consecutive unknown observations surface a visible cycle sample naming the pull request without counting a failure, and any definitive status ends the streak. Every inspection additionally records a provider-neutral qualification — workspace, pull-request number, work item, base relationship, observation time — which the orchestrator overlays onto the open-pull-request listing only where the provider projection carries no base status; a provider-supplied value is never overwritten.

A deterministically conflicting base is neither hidden nor abandoned. The conflict revision applies under the same conditions as a branch update — an open, non-draft pull request whose observed source branch still matches the retained managed workspace branch — so a draft in progress never spends repair budget. When the source-repair toggle also permits it, the cycle starts a budgeted `ci-repair` revision on the same retained branch: the provider conflict itself is the evidence, journaled as a synthetic succeeded read-only diagnosis plus a deterministic failure log instructing the agent to merge the current base into the retained branch without rebasing or force-pushing. The revision honors the shared policy gates — the daily token budget with the repair-phase guidance, the per-pull-request attempt cap counted across the recorded managed-branch journals, and repair concurrency — and a grouped source delivery passes its delivery-group scope (members, revisions, snapshots) into the conflict revision so the combined scope is preserved instead of shrinking to the root item. The journal keys workspace, pull-request number, and the exact conflicting head; a succeeded revision awaits provider reconciliation, and a later `current` observation resolves it. With source repair disabled, the conflict is recorded as an actionable cycle failure for the operator.

Conflict serialization is a separate, disabled-by-default policy control that prevents the next conflict instead of repairing the last one. While enabled, autonomy defers starting a solution whose Analyzer-predicted change surface overlaps an in-flight delivery — an open Symphony-managed pull request whose work item has not reached a terminal stage — preferring the measured changed files of the delivered implementation over the prediction whenever a verification report persisted them. A deferral spends no execution capacity, so the slot stays available for non-colliding work, and it emits a cycle sample naming the blocking pull request and its work item. Members of the same delivery are never deferred by their own pull request.

Pull-request synchronization is delivery-group aware. Executions are recorded against the group root only, so after a grouped delivery the members carry no pull-request execution of their own. A member standing in a verification stage is therefore routed through the root pull request's single per-tick observation and verification result — a merged pull request proves every member, a closed one sends every member to rework — so grouped members cannot strand while the provider shows one shared pull request.
