# Security model

The primary trust boundary is the renderer. BrowserWindow uses `nodeIntegration: false`, `contextIsolation: true`, `sandbox: true`, and `webSecurity: true`. Navigation and new-window creation are denied. A restrictive Content Security Policy limits local production content and permits the fixed localhost/WebSocket origins needed by Angular development.

Preload exposes a narrow frozen-by-context API, and Zod validation occurs in preload, Main, and Utility Process. Main accepts calls only from its window's `WebContents`. The sole native filesystem-selection capability is a typed file/directory dialog that returns user-selected absolute paths; it exposes no read, write, or enumeration primitive. Commands execute only in the Utility Process; developer-tool diagnostics use a typed allowlist for literal `--version` probes, a timeout, and `execFile` without a shell. The separate installation contract accepts only the `git`, `gh`, `codex`, `claude`, or `opencode` enum, maps it server-side to a fixed Homebrew formula or cask, strips unrelated environment variables, never invokes a shell, and verifies the command after installation. Renderer-supplied commands, package names, arguments, paths, and environment variables are impossible through the contract.

Desktop updates use a separate narrow preload surface terminating in Electron Main. Production accepts only a credential-free HTTPS origin compiled into the Main bundle and a validated Stable/Canary enum; the renderer cannot supply or receive URLs, headers, paths, signatures, or credentials. Main validates the selected installer manifest against the running platform and architecture, requires a credential-free HTTPS artifact URL, retains that URL privately, and opens it only through the named `updates.download` intent. The current GitHub Release surface is installer-only and ARM64-only: one DMG, one EXE, and one DEB are allowlisted, while ZIP, NuGet, and x64 outputs remain disabled. Platform signing and macOS notarization are optional distribution capabilities rather than release gates. Complete credential groups enable them and configured signatures are verified; absent or partial groups produce an explicitly warned ad-hoc-signed macOS bundle or unsigned Windows artifacts. The macOS ad-hoc branch has no stable Team ID and therefore disables Hardened Runtime so the process can load its embedded Electron Framework; Developer ID builds retain Hardened Runtime and are eligible for notarization. Untrusted downloads do not carry operating-system publisher trust and are installed at the operator's own discretion after checking the release-manifest SHA-256 values. Published files remain immutable, their manifest is published only after GitHub confirms exactly those three assets, installer channel pointers advance afterward, and native Squirrel feeds remain unchanged while their archive payloads are disabled. The publishing job holds a short-lived workflow token scoped to this repository rather than any long-lived distribution credential. GitHub artifact attestations remain disabled while the private user-owned repository is ineligible for them. Raw updater failures and artifact URLs do not cross into renderer state because they may contain distribution details.

Azure DevOps PAT entry is a named, bounded IPC operation rather than a generic settings field. The renderer sends the typed secret only for the explicit connect action. Electron Main requires an OS-backed encryption backend and writes an encrypted mode-`0600` blob below the private configuration root. Utility-Process startup receives only the opaque references backed by encrypted blobs; it requests one secret through a correlated, Zod-validated internal message only when the Azure DevOps adapter is about to use that connection. The connection ID and work-item source retain the workspace binding before resolution, and a resolved value stays only in Utility-Process memory. Secrets never enter status, settings, logs, renderer responses, or an eager startup synchronization. Failed replacement restores the previous encrypted credential; disconnect, workspace removal, and settings pruning remove unreferenced blobs. Other future credential mediation will follow the same operating-system-store and capability pattern. Production command policy adds executable resolution, argument schemas, environment allowlists, workspace-root enforcement, output caps, termination groups, approval policy, and redacted structured logs. GitHub Apps will receive least-privilege repository/project permissions. The bootstrap contains no credentials.

Local repository execution is restricted to enabled repository bindings that the operator explicitly adds to a Workspace Definition. Clone/fetch is a separate non-executing preparation step and disables checkout hooks, LFS smudging, and submodule initialization. AI execution requires one unambiguous configured and prepared repository; it does not require a second machine-local trust grant. Local verification retains one-time or persisted plan-capability approval, and remote or autonomous inputs cannot create those grants. Verification accepts only an opaque persisted plan ID across IPC, uses executable-specific argument schemas without a shell, receives an isolated runtime home with no provider/AI credentials, and participates in cancel-before-quit/update supervision. The host backend is explicitly not a containment boundary and does not yet enforce its declared network capability; unfamiliar verification code should remain one-time-only until the container/VM backend exists. See [Local repository verification](local-repository-verification.md).

Managed local CI has a separate disabled-by-default trust boundary. It runs the repository-owned GitHub workflow only in a fresh mount-free Lima VM created from checksum-pinned tooling and a digest-pinned Ubuntu image. The selected fixed preset bounds CPUs, memory, and maximum virtual-disk capacity, and the orchestrator permits only one such VM at a time. Registration is short-lived, repository-scoped, and carries an exact workflow-run label, so another queued workflow cannot claim the runner. The runner remains registered only until every job in that workflow run is terminal, after which Symphony removes the registration and destroys the VM. The short-lived registration token crosses into the guest through standard input, is deleted after registration, and never crosses renderer IPC or enters persisted evidence. Symphony credentials and host paths are not mounted. The VM retains outbound network access and GitHub supplies normal per-job tokens and permitted workflow secrets, so repository workflow review and GitHub event secret policy remain necessary. Quit, update, cancellation, success, and failure all supervise VM teardown; startup reconciles abandoned Symphony-owned instances. See [Managed local CI](managed-local-ci.md).

Guest image contents are configuration, never Symphony source. A workspace selects one published GitHub runner image release; Symphony resolves it into a pinned definition — Ubuntu cloud image plus SHA-256 digest, declared apt package set, declared Node.js runtime plus digest, exported environment — and persists that definition. Every artefact Symphony downloads for the guest is checksum-verified before use. The declared package set installs best effort so one renamed upstream package cannot fail an otherwise healthy run, while the small set Symphony itself requires must install. A repository may add a setup script; it is repository-owned configuration, bounded to 32 KiB, transferred through standard input rather than an argument, and executed inside the guest as the unprivileged runner user. Symphony never interprets it and never ships system requirements of a target product.

Disk exhaustion is a deny-by-default execution boundary. The orchestrator measures physical allocated blocks, not sparse virtual size, and gates AI execution, worktree creation/resume, repository preparation, verification, work-item drafting, and Local GitHub Actions against application-wide, per-workspace, Local CI, and minimum-free-space limits. Admission synchronously checks live filesystem availability and reserves the selected workload's complete bounded growth; it does not depend on completion of the slower segment inventory. The last complete inventory is cached for quota accounting across restarts, while a first launch admits only capacity that fits both configured limits and the live protected reserve. A five-second application watchdog cancels active disk-writing operations at critical pressure; Local CI adds a one-second runner watchdog. An actual measurement failure blocks new writes. Electron's disk cache is capped and cleared on startup, verification runtime homes are removed on every terminal path, and Lima HOME/cache/tmp are all relocated below the managed workspace root.

Codex automation never inherits an operator's ambient tool surface. A migrated user-home connection copies its authentication file once into its workspace-owned account home and is then persisted as isolated. Symphony links that copied account file into a separate runtime home and keeps Codex configuration, sessions, SQLite state, temporary files, and shell `HOME` below application-owned storage. Every fresh or resumed run ignores ambient user configuration and rules, reasserts its read-only or workspace-write sandbox through the highest-precedence invocation layer, disables hooks, apps, plugins, browser/computer access, notifications, bundled skills, and multi-agent execution, and replaces each repository-declared MCP transport with a disabled inert entry. This prevents a repository `.codex/config.toml` from restoring `danger-full-access` or starting unrelated local and remote tools. Repository instructions and the exact skill instructions selected by Symphony remain available as task context; they do not gain additional filesystem roots or tool permissions.

Claude Code receives separate application-owned home and supported configuration namespaces for every workspace account. Login and logout are addressed by connection ID, and runtime processes reuse only that connection's namespace. Authorization codes and provider tokens are never returned in status responses or written to settings; the one-time authorization code is validated at IPC and forwarded directly to the already-running Claude login process. Runtime executions load only the account-owned settings source and no ambient MCP configuration, so a target repository's `.claude/settings.json` and `.mcp.json` cannot add hooks, sandbox policies, plugins, output styles, or tools to an unattended run. Analysis and drafting run in plan mode and remain read-only with respect to target files. Implementation runs receive shell and web tools up front, because a headless run cannot answer permission prompts and repository trust was granted before execution; file edits stay confined to the working tree by the accept-edits mode, and Git commit and push commands are explicitly denied because Symphony owns delivery.

OpenCode automation follows the same application-owned boundary with a distinct adapter. It runs with an isolated `HOME`, `--pure`, disabled project configuration and Claude compatibility, an inline no-share/no-update policy, no subagents, and no external-directory access. Analyzer runs deny shell and edit tools. Implementation runs may edit only the isolated worktree and explicitly deny Git commit and push commands. Only the single environment variable named by the workspace connection's credential reference is copied into the child environment.

Skill discovery follows the same rule. Packaged startup reads the application-owned skill catalog and the explicitly configured repository skill root; it does not enumerate the global `~/.agents/skills` or `~/.codex/skills` trees. Import and export remain explicit file-dialog actions against the exact path selected by the operator.

Phase-1 Mobile access introduces a second, explicitly bounded trust boundary on a trusted private WLAN. It is disabled by default and binds exactly one private IPv4 interface; ambiguous or unavailable interfaces fail closed. A short-lived, single-use QR secret proposes a device, while the desktop operator must approve the matching verification code before the browser receives a random session token in an `HttpOnly`, `SameSite=Strict` cookie. Tokens are stored only as SHA-256 hashes, requests require the expected same origin, WebSocket upgrades repeat authorization, and revocation closes matching live sockets immediately. The gateway applies request-size limits, CSP and anti-sniffing headers, no-store API responses, path-safe static delivery, Zod validation, and an explicit board/ticket/execution command allowlist.

Remote GitHub automation is another disabled-by-default ingress. It accepts comment instructions only from the exact account login configured on the workspace-owned GitHub connection, restricts syntax to provider-neutral named actions, bounds feedback text, and never constructs shell commands from Issue content. Issue revisions must identify the configured account as creator or latest content editor and remain in an enabled configured Project. Workspace-local source checkpoints and receipts provide baseline protection, audit evidence, deduplication, and restart recovery; the execution keeps the triggering signal ID and actor. A successful remotely authorized Solver/revision may commit and push only its validated managed non-default branch and create or reuse the pull request; it cannot merge. See [remote GitHub automation](remote-automation.md).

[Agentic pull-request delivery](agentic-delivery.md) is independently disabled globally and per repository. Failed logs are bounded, credential-redacted, and treated as untrusted evidence; deterministic classification occurs before an assigned skill can receive them. Diagnosis is read-only. Repair requires the existing machine-local execution trust grant and remains confined to the retained managed non-default worktree. Rerun intent and commit/push/pull-request reconciliation are journaled before external mutation. Infrastructure and authorization failures cannot enter source repair, replacement pull requests need their own toggle, and no policy permits automatic merge.

Microsoft Teams feedback intake is a separate disabled-by-default ingress. It uses a client secret resolved only in the Utility Process and the resource-scoped `ChannelMessage.Read.Group` permission for one configured team. The adapter accepts only FLAMOX365 feedback Adaptive Cards with an explicit `@Symphony` request, bounds all text before AI drafting, validates classifications against live GitHub metadata, and never interprets channel content as executable instructions. Workspace-local checkpoints, receipts, and an Issue-body source marker provide baseline and duplicate protection. The mention authorizes Issue creation only; it does not authorize implementation. See [Microsoft Teams feedback intake](teams-feedback-intake.md).

Distributed GitHub execution uses a repository-scoped claim ref whose name is derived from a hash of the provider, repository, and Issue identity. Claim creation requires the same authenticated contributor and repository-content permission already needed for managed implementation branches. Assignee routing is checked before acquisition. The metadata commit contains only the GitHub login and non-secret orchestration identifiers. Phase changes and deletion require an exact persisted commit-token match, preventing one installation from releasing another installation's claim. Claims never expire automatically across a network partition.

The current local transport is plain HTTP/WebSocket and is approved only for this development POC on an explicitly trusted local network. It is not a claim of transport confidentiality and must not be used for sensitive production data until a separate TLS or remote-transport decision is accepted. Moving the client to a hosted mobile web app later replaces the transport/authentication adapter; mobile views and versioned contracts remain independent of that deployment choice.
