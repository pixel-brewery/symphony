# Frontend architecture

The Angular renderer follows the FLAMOX365 presenter and Mosaik composition baseline. `ShellView` remains a router-only root; `ShellConfig` composes the statically selected feature definitions and their lazy routes. Views render typed DTOs and send commands through their owning feature presenters and consumed ports. The retired `OrchestrationStore` facade has no replacement aggregate API. Core retains the typed client, one configuration writer, transport synchronization, readonly projections and once-only Bootstrap. Renderer source does not import Electron, Node.js, provider SDKs, credentials, or IPC channel names.

The fifteen horizontal features own their state, commands, adapters, settings cards/editors and navigation/search/quick-create/widget contributions. `provideXFeature()` registers these together. Generic capabilities are composed once, and the Settings route belongs to `frontend/setting`. [Dependency model](dependency-model.md) lists every package, subfeature and collaboration. Optional Execution, Workflow, CI and Delivery participants control which related actions are available; they do not create substitute writable state or a second configuration path.

The primary navigation is decision-oriented:

- **Home**: entry and current focus.
- **Board**: provider-neutral FlowBoard and work-item actions.
- **Pull Requests**: open delivery branches and their latest Action status.
- **Actions**: repository workflows, recent runs, and manual remote or managed-local dispatch.
- **Skills**: portable instruction packages and role assignment.
- **Settings**: Workspace Definitions and provider/account bindings.

Board, Pull Requests, and Actions share the current `WorkspaceViewScope`. One or many workspaces can be selected inline. Aggregate cards and rows show workspace color, short code, and name; interactions retain the exact workspace ID. Actions owns the repository workflow catalog and workflow-level dispatch decision; its repository-grouped navigation selects one workflow and its recent run history. A `workflow_dispatch` definition can start on GitHub or be handed to the existing managed-local VM runner after GitHub creates the exact run. When a GitHub dispatch explicitly requests the Symphony runner for a locally enabled Workspace, the idle orchestrator automatically hands it to the same local execution path. The right Runs rail remains the compact cross-route feed and does not duplicate the workflow catalog: one Action groups the GitHub scheduler/check state with its active or latest Local runner state through the shared `ciRunId`. Agent entries open the live execution drawer. Action entries load the provider-neutral job-and-step state plus the complete redacted GitHub run log through bounded IPC chunks; the renderer maps each tab-prefixed log line back to its reported job and step. The Action drawer also owns remote cancel/rerun and managed-local run/stop for exact runs. Both drawers use the same Mosaik header and one drawer-owned vertical scroll surface. The Action header orders its rows as title, explicit GitHub and Local runner states when available, and GitHub targets. Repository and concrete run navigation are separate Mosaik Anchors because they represent different destinations; the branch name labels the run target without conflating it with the repository link.

Settings is organized by Workspace Definition rather than by provider product. Each workspace card contains its Planning (Azure DevOps), Code and CI (GitHub/GitHub Actions), and AI account bindings. Right-side Mosaik drawers edit one binding at a time. Each card owns its portable export action and the page header owns workspace import. Both use the typed native path picker; the renderer never receives file contents. Tokens are write-only or represented as credential references in normal settings, while exported workspace bundles contain neither secrets nor credential references.

All routed components are standalone, OnPush, signal-backed, and use stable `test-id` surfaces. Mosaik owns Page, Card, Cell, FlowBoard, Drawer, form, Badge, empty state, and feedback components. Transient failures use the shared toast pipeline; durable execution failures stay with the affected task/run.
