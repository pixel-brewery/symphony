# Frontend architecture

The Angular renderer follows the FLAMOX365 presenter and Mosaik composition baseline. `ShellView` remains a router-only root that additionally forwards allowlisted desktop navigation targets to the router; `ShellConfig` composes the statically selected feature definitions and their lazy routes. Views render typed DTOs and send commands through their owning feature presenters and consumed ports. The retired `OrchestrationStore` facade has no replacement aggregate API. Core retains the typed client, one configuration writer, transport synchronization, readonly projections and once-only Bootstrap. Renderer source does not import Electron, Node.js, provider SDKs, credentials, or IPC channel names.

The fifteen horizontal features own their state, commands, adapters, settings cards/editors and navigation/search/quick-create/widget contributions. `provideXFeature()` registers these together. Generic capabilities are composed once. `frontend/setting` owns the main-window route `settings` (with the `projects` redirect) and the Settings surface, which hands its section navigation to the main window's sidebar and its title and actions to the window toolbar while it is open; see [Settings in the main window](window-and-navigation/settings.md). [Dependency model](dependency-model.md) lists every package, subfeature and collaboration. Optional Execution, Workflow, CI and Delivery participants control which related actions are available; they do not create substitute writable state or a second configuration path.

The primary navigation is the main window's source-list sidebar, assembled from feature-owned navigation contributions in the `desktop-main` region. Its complete contract, counts, run panel, toolbar and status bar are described in [Window chrome and navigation](window-and-navigation/README.md):

- **Overview**: start page and current focus; Symphony launches here.
- **Delivery** group: **Inbox** (decisions and updates), **Board** (provider-neutral FlowBoard and work-item actions), **Pull requests** (open delivery branches and their latest Action status), **Actions** (repository workflows, run history, and manual remote or managed-local dispatch), **Orbit**.
- **More** group: **Arcade**, only while its preference is enabled.
- **Settings**, pinned at the bottom: opens Settings in the main window with Workspace Definitions, provider/account bindings and the installed skill packages. While Settings is open its section navigation replaces every sidebar entry, and the toolbar's **Back** leads out of it. Skills has no main-navigation entry.

Board, Pull requests, and Actions share the current `WorkspaceViewScope`. The sidebar's workspace switcher selects exactly one active workspace and persists it in the view scope. Aggregate cards and rows show workspace color, short code, and name; interactions retain the exact workspace ID. Actions owns the repository workflow catalog and workflow-level dispatch decision; its repository-grouped navigation selects one workflow and its recent run history. A `workflow_dispatch` definition can start on GitHub or be handed to the existing managed-local VM runner after GitHub creates the exact run. When a GitHub dispatch explicitly requests the Symphony runner for a locally enabled Workspace, the idle orchestrator automatically hands it to the same local execution path. The sidebar run panel is the compact cross-route feed and does not duplicate the workflow catalog. Its `Actions` segment lists only the Action runs in progress and the latest failed one, each grouping the GitHub scheduler/check state with its active or latest Local runner state through the shared `ciRunId`; its `Agents` segment lists the active workspace's agents, and an agent with current work opens the live execution drawer. Action entries load the provider-neutral job-and-step state plus the complete redacted GitHub run log through bounded IPC chunks; the renderer maps each tab-prefixed log line back to its reported job and step. The Action drawer also owns remote cancel/rerun and managed-local run/stop for exact runs. Both drawers use the same Mosaik header and one drawer-owned vertical scroll surface. The Action header orders its rows as title, explicit GitHub and Local runner states when available, and GitHub targets. Repository and concrete run navigation are separate Mosaik Anchors because they represent different destinations; the branch name labels the run target without conflating it with the repository link.

Settings renders as the main-window route `/main/settings`; its sidebar replacement, routing and IPC are described in [Settings in the main window](window-and-navigation/settings.md). Every sidebar/content and list/detail split is a resizable Mosaik split with a remembered size; see [Resizable panes and scroll containment](window-and-navigation/resizable-panes.md). Settings is organized by Workspace Definition rather than by provider product. Each workspace has its own sections for its Planning (Azure DevOps), Code and CI (GitHub/GitHub Actions), and AI account bindings. Editors open as sheets over the main window and edit one binding at a time. A workspace's `Administration` section owns its portable export action and the `Workspaces` section owns workspace import. Both use the typed native path picker; the renderer never receives file contents. Tokens are write-only or represented as credential references in normal settings, while exported workspace bundles contain neither secrets nor credential references.

All routed components are standalone, OnPush, signal-backed, and use stable `test-id` surfaces. Mosaik owns Page, Card, Cell, FlowBoard, Drawer, form, Badge, empty state, and feedback components. Transient failures use the shared toast pipeline; durable execution failures stay with the affected task/run.
